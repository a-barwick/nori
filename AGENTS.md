# Nori Project Rules

1. **CI/CD owns deploys.** On authorized closeout (“wrap up,” “send it,” or “good to close thread?”), run `make check`, commit, merge solo work into `main`, and push `origin/main`. Leave rollout and release verification to CI/CD. Use PRs for team work, preserve local Xcode signing, and clean up finished worktrees and branches. Change GCP only in `infra/` (Terraform) and ship it through `main`. Never change GCP resources with `gcloud` or the Console, because the next Infrastructure run reverts changed resources and fails on new ones.
2. **Use Inkling Mini 2 for all model-backed local development and tests.** Use cloud LLMs only when Austin explicitly asks. If Inkling is unavailable or lacks a required capability, report the gap and continue with checks that can run locally. Use Nori’s guarded model client.
3. **Verify the requested outcome.** Exercise the affected flow through its normal entry point. For background work, verify completion and delivery to the expected destination.
4. **Match checks to the change.** Start with focused checks. Use deterministic simulations for durable work, retries, and approvals. Measure performance claims against a representative baseline.
5. **Check UI parity when relevant.** Follow `docs/design-system.md` and `ios/DESIGN_SYSTEM.md`. Keep Chat, Work, and More free of redundant copy and badges. Check both clients for shared behavior changes. When asked to show an iOS change, launch the exact build and appearance.
6. **Isolate test state.** Use disposable local Postgres databases for database-backed tests. Clean up the databases, servers, and worker processes you started.
7. **Respect the requested mode.** Keep reviews, test runs, and plans within their requested scope. If asked to interview first, wait for answers before planning or implementing.
8. **Verify reports before editing.** Check current code or behavior before acting on bugs, audit notes, or earlier findings.
9. **Handle routine work directly.** Run Git, build, and simulator commands yourself. Ask when a product decision, missing access, or irreversible action requires Austin.
10. **Communicate plainly and stay on scope.** Lead with what changed, what you verified, and any blockers. Record unrelated findings as follow-ups.
11. **Add docs only with Austin's approval.** Create a doc, docs-site page, plan, or notes file only after Austin explicitly approves that file. You may ask, but don't create it until he says yes. Update existing docs when the code they describe changes. Every doc follows `.agents/skills/plain-writing/SKILL.md`, and docs-site pages match the structure of the existing pages in `docs/site/`.

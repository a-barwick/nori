Task lifecycle

A task keeps one ID for its whole life, from dispatch until it finishes, fails or is stopped.

Running ⇄needs input / budget · answer, continue Waiting →checks pass Completed · Failed · Cancelled

While a task is waiting

  • It has exactly one open question and a reason: input, budget, workdesigned.
  • It doesn't expire on its own, and it survives reloads, pauses, restarts and worker deploys.
  • If a steer arrives while the task is over budget, the task asks its budget question again with a new ID.

When a task ends

  • Finished tasks stay closed, so follow-up work becomes a new task.
  • Stop is shown as requested → stopping → confirmed, and any effects that already happened are reported.

Moving between states

What happensChange
The task asks a questionRunning → waiting
The task reaches its budgetRunning → waiting, with no model call
The task finishesRunning → completed
The task can't continueRunning → failed
A Stop takes effectRunning or waiting → cancelled

In the records, a waiting task still has status running. Its open question is what makes it wait.

Commands

KindWhat it does
startCreates the task. The command ID becomes the task ID.
steerAdds new instructions and increments the revision.
answerResolves the question in question_id.
continueResolves the budget question and adds $1.
stopCancels this task and its descendantsdesigned.
subtask_resultThe runtime delivers a subtask's outcome to its parent.

Only steer and stop are corrections. Answers and continuations resume work without rewriting its instructions.

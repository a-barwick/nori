Task lifecycle

A task keeps one ID for its whole life, from dispatch until it finishes, fails or is stopped.

Running⇄question or approval · answer or decisionWaiting
Running→checks passCompleted
Running→error or budget limitFailed
Running or waiting→StopCancelled

While a task is waiting

  • It has exactly one open question or typed interaction (such as an approval card) with a stable ID and revision.
  • It doesn't expire on its own, and it survives reloads, pauses, restarts and worker deploys.
  • A steer arriving while an approval is pending supersedes the old approval so stale decisions are rejected.

When a task ends

  • Finished tasks stay closed, so follow-up work—including continuing a task that reached its budget—starts a new linked task.
  • Stop is shown as requested, stopping, then confirmed.

Moving between states

What happensChange
The task asks a question or requests approvalRunning → waiting
The task reaches its spending budgetRunning → failed (expected incomplete), with no extra model call
The task finishesRunning → completed
The task can't continueRunning → failed
A Stop takes effectRunning or waiting → cancelled

In Postgres, a waiting task still has status running; its open question or interaction is what puts it in the waiting bucket.

Commands

KindWhat it does
startCreates the task with its stable ID.
steerAdds new instructions, increments the revision, supersedes pending approvals and stops running subtasks.
answerResolves the open question or interaction in question_id.
stopCancels this task and its subtasks.
subtask_resultThe runtime delivers finished subtasks to their parent as the result of its work request.

Only steer and stop are corrections. Answers and approval responses resume work without rewriting its instructions. Continuing a budget-stopped task creates a new task via Work's continue action.

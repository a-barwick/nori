Task lifecycle

A task keeps one ID for its whole life, from dispatch until it finishes, fails or is stopped.

Running⇄question or budget · answer or continueWaiting
Running→checks passCompleted
Running→can't continueFailed
Running or waiting→StopCancelled

While a task is waiting

  • It has exactly one open question and a reason, such as input or budget.
  • It doesn't expire on its own, and it survives reloads, pauses, restarts and worker deploys.
  • If a steer arrives while the task is over budget, the task asks its budget question again with a new ID.

When a task ends

  • Finished tasks stay closed, so follow-up work becomes a new task.
  • Stop is shown as requested, stopping, then confirmed.

Moving between states

What happensChange
The task asks a questionRunning → waiting
The task reaches its budgetRunning → waiting, with no model call
The task finishesRunning → completed
The task can't continueRunning → failed
A Stop takes effectRunning or waiting → cancelled

In the records, a waiting task still has the status running. Its open question is what makes it wait.

Commands

KindWhat it does
startCreates the task with its stable ID.
steerAdds new instructions, increments the revision, and stops any running subtasks.
answerResolves the question in question_id.
continueResolves the budget question and adds $1, to the parent for a subtask.
approve, declineResolves the approval question for one exact action.
stopCancels this task and its subtasks.
subtask_resultThe runtime delivers finished subtasks to their parent, as the result of its work request.

Only steer and stop are corrections. Answers and continuations resume work without rewriting its instructions.

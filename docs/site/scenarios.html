What's in a scenario

  • Setup: the simulated state and capabilities a run needs.
  • User messages: sent one at a time, normally after each reply.
  • Check: the observable result to grade. It's never shown to the assistant.

Being on this list doesn't make something a requirement or mean it works today. Record the app version and enabled capabilities with each run.

Shared setup

  • Time is frozen at Friday November 6, 2026, 09:00 in America/Los_Angeles unless a scenario says otherwise.
  • The fictional user lives in Oakland, California. “This weekend” is November 7–8, and the upcoming Monday is November 9.
  • All contacts, messages, events and purchases are fictional. Side effects run against isolated simulated state.
  • Attachment cases need the synthetic file itself. Text saying a file exists isn't enough.

Running a conversation

  • Start with a clean conversation and reset simulated state between scenarios. Preserve state within a scenario, including explicit reloads or new-session transitions.
  • Send numbered user messages one at a time, normally after the assistant responds. Deliver an interruption during work only where the setup says to.
  • Keep fixture facts and success checks outside the assistant's user messages. Expose facts through the appropriate tool responses, attachments, prior history, or existing memory.
  • Treat later messages as conversational beats, not a blind transcript. Supply an answer when the assistant asks the corresponding question; send a revision after the relevant draft or result. If an extra clarification is needed, answer only from the scenario's facts and keep the same voice.
  • A simulated user must not invent missing facts, reveal the grader's checklist, accept an incorrect result just to finish, or rescue the assistant with unsolicited tool instructions. If essential facts are absent from the scenario, mark the run underspecified and repair the fixture before comparing results.
  • Use the application's real approval interaction when its policy requires one. A conversational “send that” identifies the intended action but does not bypass a required approval control.
  • End when the goal is met, a supported limitation is clearly explained, or the interaction stalls. Use a provisional cap of 12 total user messages, including clarifications, so a loop is visible.

Why these scenarios

These sources motivated the coverage. They don't make it a representative sample or a validated benchmark.

EvidenceFinding relevant to this collectionDesign choice
OpenAI consumer usage study, 2025Practical guidance, information seeking, and writing account for about three quarters of conversations. The study separately labels messages as asking, doing, or expressing.Include useful answers, everyday advice, writing, and conversation alongside tool-driven tasks.
Anthropic Economic Index, September 2025Its interaction categories distinguish delegation, feedback loops, learning, iterative work, and validation.Vary how the user collaborates, not just the topic they ask about.
WildChat, 2024Consented real conversations include multiple turns and many languages. Its opt-in sample is a particular population, not a census of assistant users.Include fragments, natural follow-ups, mixed languages, and changes of tone. All prompts here are newly written synthetic examples.

τ²-bench, 2025Tests environments where both the user and assistant can change the world.Include troubleshooting in which the user performs a step and reports a new state.

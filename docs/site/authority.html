Tool authority

A task acts within the user's request and permission rules. The runtime checks the task revision, pins the tool definition digest and records the operation before dispatch.

Task stepCalls a tool. The call names its task revision, pinned definition digest and operation ID.

RuntimePrepares the call, computes its action digest, then checks deny rules, approvals and allow rules.

MCP server or provider adapterThe runtime checks the revision again, counts the attempt, calls it and saves the outcome.

Before a tool runs

  • Each call belongs to a task, instruction revision, pinned extension digest and operation ID. A correction or Stop fences stale work.
  • Connecting an MCP server or account grants no execution authority on its own. Every external call passes through core/internal/permissions and core/internal/invoke.
  • A subtask can inherit a read-only limit from its parent. Loading a capability adds tool definitions to the model request without granting permission.
  • Attachments, search results and MCP tool outputs are untrusted data. They carry no authority to dispatch or steer tasks or approve actions.

Recovering an interrupted call

  • The operation record holds the action digest and summary, so a restarted worker can find the call.
  • If the worker stops before the result is saved, the runtime asks the provider adapter to reconcile when it can. Otherwise it saves the outcome as uncertain.
  • A write is never repeated automatically. Only reads and control tools can retry.
  • While a write is unresolved, the runtime admits no other write. The task asks the user with request_input, and the answer lets later writes run.
  • Stop ends the task and keeps all operation evidence about what may already have happened.

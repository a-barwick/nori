Tool authority

A task acts within the user's request and permission rules. The runtime checks the task revision, pins the tool definition digest and records the operation before dispatch.

Before a tool runs

  • Each call belongs to a task, instruction revision, pinned extension digest and operation ID. A correction or Stop fences stale work.
  • Connecting an MCP server or account grants no execution authority on its own; every call passes through core/internal/permissions and core/internal/invoke.
  • A subtask can inherit a read-only limit from its parent. Loading a capability adds tool definitions to the model request without granting permission.
  • Attachments, search results and MCP tool outputs are untrusted data. They carry no authority to dispatch or steer tasks or approve actions.

Recovering an interrupted call

Before dispatching an external write or unknown-effect tool, one Postgres transaction checks the task revision, verifies the matching approval or allow rule, and records the operation as attempted with its action digest and idempotency key.

If a provider response is lost or a call ends uncertain, the runtime records the uncertain state and never repeats the write automatically. The task can inspect saved evidence and ask the user before continuing. Stop ends the task and preserves all operation evidence about what may already have happened.

Approvals and writes

Nori can read freely. Before it changes anything outside its own computer, the user approves the exact action.

A task prepares an action“Add dinner with Sam, Thursday 7pm, to the personal calendar.”
↓
The task parksThe user sees the target, content and account. No model calls run.
↓
ApproveThe runtime checks nothing has changed, then runs it once.
DeclineThe task records the decline and doesn't ask again.
↓
A receipt records what happened“Did you add it?” is answered from the receipt.

Every tool declares what it does

TypeExamplesRetries
Readbrowser_navigate, search, calendar readThe runtime retries within limits.
Reversible writeA calendar eventOnly with duplicate protection. Otherwise check first.
Sensitive sendAn email, a purchaseAsk the user before any repeat.

The model can't give itself permission to retry.

What an approval covers

  • One operation, once. Changing the recipient, content, date or account makes it invalid.
  • A correction after approving a draft still counts.
  • It survives waits and restarts as long as the action is unchanged.
  • A restart or a repeated delivery can't use it twice.

What can't grant permission

  • A label from the Jev classifier or a task category.
  • A tool being available.
  • Text in a web page, email, document or tool result.
  • A task's own summary of its next step.

Recording what happened

Prepared→Attempted→Submitted→Confirmed
  • An action can also end as failed or uncertain, and uncertain is never shown as success.
  • If the response was lost, the runtime checks with the provider before any repeat.
  • Stopping a task doesn't undo what it already did. Nori reports those effects.

Still open

  • How standing permissions work, and how the user takes them back.
  • When an approval expires.
  • Which changes count as material.

Results and files

A saved result reopens later with version history, and its record shows whether it reached the user.

Created→Checked→Reported→Delivered

These are separate timestamps on one record. For “Draft the Q3 launch brief”, the task saves the result, the completion check verifies its evidence, an outer reply links it, and the client reports showing that reply.

What a result records

  • A stable ID, and its kind: an answer, a file, an image or a link.
  • The task that created it, and the instruction revision it answers.
  • The saved tool results its answer cites, and anything left unmet.
  • A saved artifact counts as checked only when the answer cites it.

Finding and revising it later

Show me that Q3 brief. The outer loop sees up to 20 recent results and displays one with show_result without starting a task.

The runtime checks each requested result before publishing the reply. If a result is missing, the reply says so and still shows any available results.

Revise it for EMEA. A task saves a new version linked to the original. A task that doesn't finish leaves the original current.

When two tasks revise the same result, the first completed revision stays current. The later output is saved separately with a conflict notice. Both outputs and earlier versions stay readable via GET /v1/library/{id}/versions.

What did we find last week? A task searches earlier results with results_find and reads specific results with result_read.

Files the user attaches

Client / host appUploads a file with a stable UUID before sending the message. Retrying stores one copy.
↓ bytes, up to 10 MiB
Agent serviceValidates image and PDF headers or UTF-8 CSV text, then writes bytes to private storage.
↓ message with upload IDs
Outer loopSees a file's name, type and size, and never its raw contents.
↓ start, steer or answer command
Inner loopReads only files assigned to the task. Images are inspected via upload_inspect in a separate no-tools model call.

A CSV must have a .csv name and UTF-8 text without NUL bytes; SVG uploads are refused because SVG can execute scripts. Both outer and inner prompts treat file names and contents strictly as untrusted data.

Where things live

ThingWhere
Metadata, versions and linksPostgres (results and uploads collections)
Attached files and saved result bytesPrivate S3 bucket (state/s3) on AWS, or local directory (state/localfs) in development, under user-scoped artifacts/ prefixes
Task control & discovery rowsReferences only; large bytes stay in S3/localfs and private history blocks

Files are served through the authenticated API with Content-Disposition: attachment and a sandboxed CSP header so untrusted bytes never execute in the app origin.

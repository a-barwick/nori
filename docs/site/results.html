Results and files

A saved result reopens later, and its record shows whether it reached the user.

Created→Checked→Reported→Delivered

These are separate times on one record. For “Write up the Tucson forecast”, the task saves the file, the completion check accepts it, a reply names it, and the browser reports showing that reply.

What a result records

  • A stable ID, and its kind: an answer, a file, a screenshot or a link.
  • The task that made it, and the instruction revision it answers.
  • The saved tool results its answer cites, and anything left unmet.
  • A file counts as checked only if the answer cites it.

Finding it later

Show me that research. The outer loop sees up to 20 recent results and shows one without starting a task.

The runtime checks each requested result before publishing the reply. If a result is missing, the reply says so and still shows any available results.

Revise it for Thursday. A task saves a new result that links to the original. A task that doesn't finish leaves the original current.

When two tasks revise the same result, the first completed revision stays current. The later output is saved separately with a conflict notice. Both outputs and earlier versions stay readable.

What happened with Tom? A task searches earlier results by word, along with older tasks that have no result record.

Outer loopSees a file's name, type and size, and never its contents.
↓ start, steer or answer command
Inner loopReads only files it was given. Images go to a no-tools model call.
↓ read-only copy
ComputerShell commands read PDFs and CSVs there, away from the worker's credentials.

A CSV must have a .csv name and UTF-8 text without NUL bytes. The upload check does not parse its rows.

Both prompts mark file contents and names as untrusted data. Approvals still guard calendar and email writes. Shell has public internet, and only the prompt's instruction to treat a file as data guards against a hidden instruction there.

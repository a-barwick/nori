Meta Muse

Security architecture

How We Built Safety Into Muse · September 8, 2026 · Architecture disclosure.

Describes a dedicated Linux VM, an agent runtime container using systemd-nspawn, host-side privileged services, a credential service, and Sentinel permission enforcement. Surrogate credentials are replaced at the network boundary; approval grants are scoped capabilities. The agent’s editable environment is separated from the components enforcing policy. Useful for Nori’s credential and permission boundaries. Confidential VM support was described as forthcoming, not a universal launch guarantee.

Model memory and sustained work

Muse Wonder · October 12, 2026 · Model capability and evaluation disclosure.

Discusses Active Memory, Active Focus, FocusBench and SWE-Marathon. Useful for separating relevant recall from sustained task completion. The post describes Wonder as coming to Muse experiences; it does not establish that every Muse interaction already uses it, nor expose a consumer-agent control API.

Voice and avatar implementation

Bringing Your Muse to Life · September 23, 2026 · Subsystem architecture.

Explains streaming speech tokens, audio-conditioned avatar generation, causal video chunks and serving optimizations. Relevant if Nori adds voice or an avatar; not a source for background-task orchestration.

Product contract

Muse official product page · Living product page, checked October 25.

Covers dedicated persistent computer access, connected apps, background work and approvals. Use as a product comparison, not independent reliability evidence.

The reviewed sources do not establish a public full harness, agent-management SDK, memory-retrieval implementation, or queue/checkpoint/replay design.

Grok Bot

Persistent agent product design

Designing Grok Bot for a world of persistent agents · September 3, 2026 · Product architecture and design rationale.

Organizes the product around Bots, chats, reusable prompts/skills/routines, tools and artifacts. Distinguishes account-level tools and skills from Bot-specific memory and routines. Useful for role-specific assistants and clear working, waiting and blocked states; not a backend specification.

Shared computer and durable state

Use the computer and apps · Living operational documentation, checked October 25.

All Bots on one account share a persistent computer, files, browser logins and CLI credentials. Separate screens permit parallel work but are not security boundaries. Different users have isolated computers. The documentation distinguishes durable workspace state from replaceable runtime state and explains recovery. Useful for deciding which Nori resources belong to a user versus an individual task.

Reusable procedures and triggers

Skills and routines · Living usage documentation, checked October 25.

Separates a reusable method from a Bot-owned workflow triggered by a schedule or supported event. Covers failure handling, real-effect tests, retries and approval boundaries. Useful for designing ownership and history; does not disclose scheduler internals.

Network and connector boundaries

Grok Bot security · Living security documentation, checked October 25.

Computer network controls and remote connector/MCP controls are separate paths. A VM egress allowlist should not be assumed to govern every connector call. Useful for Nori’s policy coverage across browser, shell and APIs; enterprise controls may differ from self-serve features.

Launch and positioning

Introducing Grok Bot · August 11, 2026 · Product announcement.

Describes persistent named teammates, group coordination, remembered workflows and unattended work. Useful for interaction patterns, not measured completion rates.

The reviewed sources do not expose complete Bot runtime code, exact memory retrieval, queue/replay semantics or a standalone public Bot-management SDK. Grok model APIs are a different interface.

OpenAI dots

Safety and credential architecture

How we build safety, security, and privacy into dots · September 29, 2026 · Architecture and security disclosure.

Describes isolated cloud workspaces, separate coordination and safety enforcement, protected sign-ins and an independent pre-action review. Proactive research is separated from actions that modify connected systems. Useful for designing a boundary between gathering information and acting on it; workspace isolation alone is not authorization.

Tasks and memory behavior

Tasks and memory · Living product documentation, checked October 25.

Explains pause/wake continuation, recurring schedules, parallel background agents and separate task threads. Distinguishes current conversation context, retrieved conversations, ChatGPT memory and dot-specific notes. Task completion status is not itself proof of a successful outcome. Useful for Nori’s primary conversation coordinating multiple tasks without treating every task as the same context.

Persistence and approval evaluations

GPT-6 Astra System Card dots appendix · Public system-card appendix, checked October 25.

Describes persistence tests, simulated time budgets, clock/wait tools and harness comparisons. Includes malicious email, changing permissions, chained tasks and action-review tests. Useful as an evaluation checklist for Nori. Reported evaluation failure rates are scenario-specific, not estimates of production incident rates.

Privacy and deletion behavior

Dots privacy, security, and safety FAQs · Living documentation, checked October 25.

Covers plugin permissions, memory exchange, retention, disconnection and deletion. Disconnecting a source is different from removing previously retained information; deleting a dot is different from deleting separately stored files. Useful for designing understandable memory controls.

Launch and positioning

Introducing dots · September 29, 2026 · Product announcement.

Describes an ongoing assistant with concurrent work, a cloud computer and cross-channel context. Preview features should not be treated as generally available.

The reviewed sources do not completely specify storage schemas, memory ranking/compaction, queue/checkpoint/replay semantics or cost per completed task. Public agent SDKs are not evidence that dots uses those exact implementations.

Implications for Nori

These are design conclusions, not additional vendor disclosures:

  • Keep user files and browser state separate from the services enforcing permissions and protecting credentials.
  • Give each task explicit status, ownership, cancellation and recovery behavior; a long chat history is not a task database.
  • Treat memory retrieval, scheduled triggers, computer persistence and authorization as separate mechanisms.
  • Test changes in user instructions and permissions across intervening tasks, not only happy-path completion.
  • Measure completed work, correction time and cost. Product pages establish intended behavior, not reliability or retention.

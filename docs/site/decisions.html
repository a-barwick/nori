Subtasks

DecisionWhyRejectedDate
A parent task parks on request_work, and a subtask's outcome is delivered back in the same transaction that saves it.It's the parent-waits-for-children pattern from BullMQ flows and Celery chords, built on the existing outbox. No model call is spent on delivery.Relaying every result through an outer turn. Temporal child workflows. Signals between workflows. A separate Pub/Sub system.Oct 25
The parent owns the budget, and stopping a parent stops its subtasks.Re-issuing or splitting work can't reset spending.Separate budgets per subtask.Oct 25
A turn with only a work request can dispatch for that request or answer it, and nothing else.The outer loop has to act on the request without a user message, and text from a task shouldn't be able to approve, continue, stop or steer.Keeping every notification turn command-free. Letting that turn use all commands.Nov 1
A dispatch for a request names its question ID.A late dispatch can't attach to a newer request from the same task.Naming only the parent task.Nov 1
A correction to a waiting parent closes its request and stops its subtasks.They were started for the old instructions and spend the parent's budget.Keeping them running and delivering a late result.Nov 1
One request starts up to 4 subtasks in one response, and a subtask can't have subtasks.Results arrive together, and one level keeps Stop and the budget simple.Unlimited nesting. Adding subtasks to a request across turns.Nov 1
A budget question appears on the task that reached the limit, and continue adds $1 to the parent.A parent waiting on its request already has one open question.Moving the question to the parent.Nov 1

Approvals and writes

DecisionWhyRejectedDate
Every calendar write and email send asks for approval, even after a direct request such as “just change my calendar”.The first writes need one rule the user can check. Standing permissions can come later.Treating the current request as enough permission.Nov 1
An approval binds one saved action. Any change to the account, calendar, event, title, time, recipient or text voids it, and it has no timer.The runtime sends the saved action, so model output after the approval can't change what runs.Choosing which changes count as material. An expiry timer.Nov 1
The user can approve in the panel or with standalone assent to the immediately preceding exact approval prompt. Approval in the assistant conversation binds the saved task and question IDs.Ambiguous or mixed replies need clarification or the panel. The runtime checks this binding without another model call.Approving from a word inside another request. Letting task output choose the approval target.Nov 4
The provider's record is the source for what happened. Write IDs come from the exact action, and the runtime looks them up before writing and after a lost response.A lost response leaves the provider as the only record of the effect, and a second task can check it too.A separate receipt store. Retrying automatically after a lost response.Nov 1
Approval covers the write tools only. Shell and browser have no approval step, and the Google token stays off the computer.The runtime can't tell what a shell command changes.Classifying shell commands. Filtering the computer's network.Nov 1
A move is refused on an event with other attendees.Moving it changes their copies too, and with notifications off they wouldn't be told.Moving it silently. Notifying attendees in the first version.Nov 1
Scenario 027 sends an email through Gmail to an address the run is given, and the task reads the sent message's headers.A send through Gmail showed that Gmail replaces a supplied Message-ID, which a local fixture can't show.A simulated outbox tool. A calendar version of the scenario.Nov 1
Writes go to one configured calendar.A worker's approval and its checks then cover one known target.Writing to any selected calendar.Nov 1
A move fails if the event changed after the user saw it.The approval covered the event as the user saw it.Moving whatever the event has become.Nov 1
A write is refused once its start time has passed.A past time can't be what the user meant to schedule.Writing an event that has already started.Nov 1
Before asking, the runtime reads the provider, and the card shows the account, calendar, event, old time and new time. The move tool takes the event's ID and the new time.The user approves what the provider holds now.Asking from the model's description alone.Nov 1
An email carries an ID from the exact action in its own header, and the runtime looks for it in the latest 10 sent messages, because the mail scope it holds can read headers but can't search. Gmail replaces a supplied Message-ID, so that header can't carry it.It finds a lost send without a scope that reads message bodies.Asking for full mailbox read access.Nov 1
Attempted means the approval is used and the provider hasn't answered. Failed means the provider refused the write, or a later read shows it didn't happen.A failed write can be proposed again, and an attempted one can't until the provider is read.Treating any error as failed.Nov 1
The calendar tools have no attendee field and send no notifications.A request to read or hold time can't invite anyone by accident.An invitation option in the first version.Nov 1
One transaction checks the task's instructions and marks the approval used. A repeat finds it used and only reads the provider.A restart or a repeated delivery can't send twice.Tracking use in workflow state alone.Nov 1
The write tools are calendar_create and calendar_move, which are reversible writes, and email_send, which is a sensitive send.The tools match the first scenarios and the action policy. Each confirms with a follow-up read of the event or the sent message.A general provider tool the model fills in.Nov 1
A write is prepared, attempted, submitted or confirmed. Submitted means the provider accepted it and a follow-up read didn't complete. It can also end as declined, voided, failed or uncertain.A provider's answer and a follow-up read are different evidence, and the outer loop reports what each shows.A single done flag.Nov 1
After a decline the same action is refused. After a correction the task proposes again. If the provider can't be read, the task asks the user.A decline is a decision, a correction changes what the user wants, and the user decides what to do about an unknown effect.Asking again after a decline. Repeating a write the provider can't confirm.Nov 1
The one-time connect command now also grants changing calendar events, sending mail and reading sent mail headers, and saves to Secret Manager as well as .env. This replaces the read-only connection from Oct 31.The write tools need these scopes, and production needs the same connection.A second Google connection for writes.Nov 1

Finishing and budgets

DecisionWhyRejectedDate
The model proposes complete, the runtime checks the records, and the outer loop compares the answer with the cited results.A correct backup answer scored partly at 0.64 and stopped on a question. Tool results already show what happened.A Jev verdict with a 0.8 threshold, used from Oct 25 to Nov 1. Treating a tool-free answer as done.Nov 1
A tool that changes something must come with a way to confirm the change: its own result, such as a 200 and an ID, or a follow-up read.Evidence comes from the provider or the system that changed, and the outer loop can read it.A runtime rule that every write needs a follow-up read, because the runtime can't tell what a shell command changed.Nov 1
Each top-level task starts with $1 of model cost, and continue adds $1.Cost is measurable and easy to explain.Six model calls and twelve tool calls per task.Oct 25
Retries follow each tool's action policy: read, reversible write or sensitive send.The model can't grant itself a retry, and repeating a write can duplicate its effect.Retrying whole activities or the whole loop.Oct 25

Results and files

DecisionWhyRejectedDate
Each assistant message, task or result change adds a numbered log event in the same transaction. One assistant stream per owner reads the record's current state.Numbers follow commit order, so the log can't miss a change or send one out of order. The cost is that these writes queue on one document.Ordering by commit timestamp, which can tie. Copying whole records into the log. WebSockets, because commands already use POST. One stream per thread.Nov 2
The assistant client follows the stream only while a tab is visible and something has run in the last 5 minutes.An open stream keeps the service awake.A stream for every open tab. Polling as a fallback.Nov 2
The assistant reply arrives whole. Independent chat adds streamed text, as recorded below.The outer model returns JSON, and streaming it needs partial parsing and new cost accounting.Streaming reply text in this milestone.Nov 2
Files upload through the web server, up to 10 MiB each.The same path runs locally and hosted. A probe through Agent Runtime accepted 16 MiB and refused 33 MiB.Signed Cloud Storage URLs, which need bucket CORS and signing rights.Nov 2
Assistant tasks read PDFs and CSVs on the computer, and images in a no-tools model call.Parsing an untrusted file stays away from the worker's credentials.Parsing PDFs in the worker.Nov 2
Editing a result always makes a new revision.The old version stays as history, and a changed draft has no earlier approval.Editing in place.Nov 2
The first completed revision of a result stays current. A competing output is saved separately with a conflict notice.Both outputs and the existing history stay readable.Overwriting the current revision. Revision branches or automatic merging.Nov 4
Results and files are kept with no expiry.One owner produces few of them, and there's no evidence yet for a rule.A lifecycle rule now.Nov 2
The browser previews images and PDFs only, and SVG uploads are refused.SVG can run scripts.Previewing other types.Nov 2
Delivered means a visible browser tab reported showing the reply.A saved reply doesn't show that anyone saw it.Counting a saved reply as delivered.Nov 2
A failed shell command blocks later ones unless it can't have changed anything, and an answer to a question naming it releases it.A retry could repeat an effect, and the block used to have no way out.Removing the block. Releasing only on the words "nothing changed".Nov 2

DecisionWhyRejectedDate
If two clients could disagree about something, the service owns it.Clients that build prompts or parse model output drift apart.State in browser storage, as in the first demo.Nov 4
The assistant and independent chat use one agent service and the same owner authentication.Both clients use the configured providers, spending controls and tool approval implementation.A separate backend and separate credentials for the chat client.Nov 4
Keep existing assistant records and add separate chat records, files and events.Old message IDs, tasks, files and pending questions remain readable through existing routes.Moving assistant records into a new format before adding chat.Nov 4
Chat saves streamed text at most every 400 ms, and each event carries only the messages that save changed.In a local test on Nov 4, saving every token with a full snapshot took 196 saves for a 2 KB reply, and a full replay of a five-turn chat was 6.2 MB.

Subtasks

DecisionWhyRejectedDate
A parent task parks on request_work, and a subtask's outcome is delivered back in the same transaction that saves it.It's the parent-waits-for-children pattern from BullMQ flows and Celery chords, built on the existing outbox. No model call is spent on delivery.Relaying every result through an outer turn. Temporal child workflows. Signals between workflows. A separate Pub/Sub system.Oct 25
The parent owns the budget, and stopping a parent stops its subtasks.Re-issuing or splitting work can't reset spending.Separate budgets per subtask.Oct 25

Finishing and budgets

DecisionWhyRejectedDate
The model proposes complete, then record checks and one Jev question decide. A yes needs 0.8 confidence, with at most 2 corrections.Tool success doesn't mean the request was satisfied.Treating a tool-free answer as done, which remains only in retained older workflows.Oct 25
Each top-level task starts with $1 of model cost, and continue adds $1.Cost is measurable and easy to explain.Six model calls and twelve tool calls per task.Oct 25
Retries follow each tool's action policy: read, reversible write or sensitive send.The model can't grant itself a retry, and repeating a write can duplicate its effect.Retrying whole activities or the whole loop.Oct 25

Temporal Cloud runs one workflow per task.Durable waits and timers with no orchestration service to host.Self-hosted Temporal and Postgres on one VM. A separate conversation workflow.Oct 24
Firestore owns accepted intent, and a relay delivers it to Temporal until acknowledged.The two services can't share a transaction, so accepted work has to survive a crash between them.Writing to Temporal directly on acceptance.Oct 24
Cloud Tasks wakes the conversation service.It keeps the current hosting and has no resident worker. Chat stays up when task execution is paused.Using task workers, which pause would switch off. A Firestore Eventarc trigger, which targets Cloud Run while the service is on Agent Runtime.Oct 25

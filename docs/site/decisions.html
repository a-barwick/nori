Subtasks

DecisionWhyRejectedDate
A parent task parks on request_work, and a subtask's outcome is delivered back in the same transaction that saves it.It's the parent-waits-for-children pattern from BullMQ flows and Celery chords, built on the existing outbox. No model call is spent on delivery.Relaying every result through an outer turn. Temporal child workflows. Signals between workflows. A separate Pub/Sub system.Oct 25
The parent owns the budget, and stopping a parent stops its subtasks.Re-issuing or splitting work can't reset spending.Separate budgets per subtask.Oct 25
A turn with only a work request can dispatch for that request or answer it, and nothing else.The outer loop has to act on the request without a user message, and text from a task shouldn't be able to approve, continue, stop or steer.Keeping every notification turn command-free. Letting that turn use all commands.Nov 1
A dispatch for a request names its question ID.A late dispatch can't attach to a newer request from the same task.Naming only the parent task.Nov 1
A correction to a waiting parent closes its request and stops its subtasks.They were started for the old instructions and spend the parent's budget.Keeping them running and delivering a late result.Nov 1
One request starts up to 4 subtasks in one response, and a subtask can't have subtasks.Results arrive together, and one level keeps Stop and the budget simple.Unlimited nesting. Adding subtasks to a request across turns.Nov 1
A budget question appears on the task that reached the limit, and continue adds $1 to the parent.A parent waiting on its request already has one open question.Moving the question to the parent.Nov 1

Approvals and writes

DecisionWhyRejectedDate

An approval binds one saved action. Any change to the account, calendar, event, title, time, recipient or text voids it, and it has no timer.The runtime sends the saved action, so model output after the approval can't change what runs.Choosing which changes count as material. An expiry timer.Nov 1
The user can approve with the panel button or a chat reply. Only a turn started by the user's message can issue the command, and that message needs a word of assent.A chat reply fits the single conversation, and a task event can't approve its own action.Button only. Letting a turn started by a task event approve.Nov 1
The provider's record is the source for what happened. Retrying automatically after a lost response.Nov 1
Approval covers the write tools only. Shell and browser have no approval step, and the Google token stays off the computer.The runtime can't tell what a shell command changes.Classifying shell commands. Filtering the computer's network.Nov 1
A move is refused on an event with other attendees.Moving it changes their copies too, and with notifications off they wouldn't be told.Moving it silently. Notifying attendees in the first version.Nov 1

Writes go to one configured calendar.A worker's approval and its checks then cover one known target.Writing to any selected calendar.Nov 1
A move fails if the event changed after the user saw it.The approval covered the event as the user saw it.Moving whatever the event has become.Nov 1
A write is refused once its start time has passed.A past time can't be what the user meant to schedule.Writing an event that has already started.Nov 1
Before asking, the runtime reads the provider, and the card shows the account, calendar, event, old time and new time. The move tool takes the event's ID and the new time.The user approves what the provider holds now.Asking from the model's description alone.Nov 1

Attempted means the approval is used and the provider hasn't answered. Failed means the provider refused the write, or a later read shows it didn't happen.A failed write can be proposed again, and an attempted one can't until the provider is read.Treating any error as failed.Nov 1
The calendar tools have no attendee field and send no notifications.A request to read or hold time can't invite anyone by accident.An invitation option in the first version.Nov 1

After a decline the same action is refused. After a correction the task proposes again. Repeating a write the provider can't confirm.Nov 1

Finishing and budgets

DecisionWhyRejectedDate
The model proposes complete, the runtime checks the records, and the outer loop compares the answer with the cited results.A correct backup answer scored partly at 0.64 and stopped on a question. Tool results already show what happened.A Jev verdict with a 0.8 threshold, used from Oct 25 to Nov 1. Treating a tool-free answer as done.Nov 1
A tool that changes something must come with a way to confirm the change: its own result, such as a 200 and an ID, or a follow-up read.Evidence comes from the provider or the system that changed, and the outer loop can read it.A runtime rule that every write needs a follow-up read, because the runtime can't tell what a shell command changed.Nov 1
Each top-level task starts with $1 of model cost, and continue adds $1.Cost is measurable and easy to explain.Six model calls and twelve tool calls per task.Oct 25

Route and payload reference

These are the user-scoped agent-service paths. The Next.js server resolves the verified email through POST /api/users/resolve, then prefixes these paths with /users/<id>/ using its own credentials. Browser headers, JSON and query parameters never choose the user. Files and event cursors share the same user scope.

Chats have no conversation-length limit. The model receives the newest complete message groups that fit within 32 messages and 96 KiB of encoded history, stopping at the first group that would exceed either bound. Older messages are omitted, not summarized; saved history is unchanged. Current-turn tool results are separately bounded to eight steps and 16 KiB per result. No new model or shared memory is involved.

Firestore stores each message separately, with a 256 KiB encoded-message ceiling; individual user inputs, model output and tool results also have their own bounds. Events carry at most one changed message. Existing inline chat history migrates atomically on its next update. Reads, duplicate-input checks and write recovery retain access to older records. Unresolved writes stay indexed until recovery records their outcome. A stream reset reloads the latest page; older history can be loaded again.

turnPolicy: "reject_while_running" means chat returns 409 while a reply is open. "fold_into_turn" means the assistant accepts new input and restarts its reply after a quiet second. After three restarts, or when a batch fills, it freezes that turn and queues later input for the next one.

The shared contract uses typed parts because plain text cannot preserve files, pages, images, links and offers. Each message has id, role, status, parts; unknown non-text parts have a fallback. Existing text, chat sequence, attachments and operations remain. Input parts accept only text and uploaded attachment IDs; host-supplied offer or artifact parts grant no authority.

Operations retain their existing evidence fields and add owner: {type: "message" | "task", id}. This preserves where work actually ran. attempted or uncertain does not mean confirmed; keep outcome, action, result_ref, attempt, cleared intact. Foreground operations may include an inline result. Assistant results remain referenced by their saved history ID. No new approval step is introduced.

Reusing a message ID with different content returns HTTP 409. If wake delivery fails after acceptance, HTTP 503 includes accepted: true; retry the same ID.

The event stream

Both conversation modes use unnamed server-sent events with {seq, kind, conversation, messages}. The SSE ID equals seq. Start from the snapshot's position, then send ?after=N or Last-Event-ID. Upsert messages by ID and merge the conversation header. Streams end after 150 seconds; reconnect from the last position. A gap or kind: "reset" requires a fresh snapshot.

Chat kinds include input.accepted, reply.updated, tool.updated, turn.completed, turn.cancelled, turn.failed. Operations travel on their changed message. Assistant kinds include message, conversation, task, result, operation, schedule, offer, read_position; their payloads use messages, tasks, results, operations, schedules, offers, readPosition. These extras never appear in chat. A conversation event also carries pending/processing state. Heartbeats are SSE comments and do not advance the cursor.

Assistant event records are resolved by the server, so hosts do not fetch each referenced record. Events are consecutive and are not coalesced. Payloads are current upserts, not historical versions: a replay can already include a later change. A removed referenced record yields missing: true while preserving its sequence. Upsert extras by ID; operations are keyed by owner and ID. Fetch saved operations for a task when its panel opens. Unknown kinds may be ignored after advancing the cursor.

Stopping chat preserves partial text and saved external-action outcomes. Stopping the assistant fences its reply so a late provider response cannot publish or dispatch more commands. Already accepted tasks continue, newer inputs stay queued, and retained evidence is unchanged. Stop a task separately through the existing task API.

The existing /api/*, /v1/snapshot and /v1/events contracts remain available to the current web client. No frontend migration is required.

Optional assistant features

All five settings default to true. Set a value to false to disable it; other values are rejected at startup.

SettingEffect
NORI_BACKGROUND_TASKS_ENABLEDFalse selects chat-only mode: no Temporal connection, task worker, Jev or OpenRouter key. Assistant routes return HTTP 501 with code: "not_enabled". Saved assistant work remains for re-enabling.
NORI_JEV_ENABLEDSkips intent classification and removes the Jev key requirement. The outer model and command admission rules remain.
NORI_COMPUTER_ENABLEDDisables computer connections in API and worker processes. Other tools remain available.
NORI_CALENDAR_OFFERS_ENABLEDDisables calendar checks and offer delivery/decisions. Retained offers remain saved.
NORI_SCHEDULES_ENABLEDDisables schedule creation, changes and execution. Existing schedules remain saved; a retained unpublished schedule change waits for re-enabling.

With all five off, run nori-local with a store, local artifact directory, provisioned user and OPENAI_API_KEY. Its in-process loop handles chat delivery without a queue or Temporal. See core/infrastructure/local/README.md for configuration. Hosted deployments retain their normal authentication and wake transport. Chat never receives background tasks, results, schedules or offers. Model roles and usage reporting are unchanged.

Shared read positions

  • The assistant client reports a reply only when it enters the visible conversation viewport.
  • The service saves that read position and its event together. Older reports cannot move it backward.
  • Other assistant sessions receive the mark. Independent chat does not report shared read positions.

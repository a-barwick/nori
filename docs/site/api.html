Service API

Clients send messages and task commands to the agent service over HTTP, and read back snapshots.

Endpoints

EndpointWhat it does
POST /api/sessionReturns the conversation and tasks.
POST /api/statusReturns version and busy, a cheap check for whether the session changed.
POST /api/turnSends a message. Returns 202 once it's saved.
POST /api/commandSends a task command, such as an answer or a continue.
POST /api/inputSends an explicit update to one task.
POST /api/cancelRequests Stop for one task.
POST /api/traceReads the debug steps for one task.
POST /api/artifactReads a saved screenshot.
POST /api/processCloud Tasks calls this to process saved messages. Clients don't call it.
POST /api/resumeRedelivers saved commands and wakes tasks. Clients don't call it.

The web client is the only caller. It reaches these endpoints through its Next.js server. While work is running, it polls /api/status, as Polling describes.

Status fieldBehavior
ReadsThe paused flag, the conversation counters, the active turn and the open tasks. A snapshot also reads messages, finished tasks, attempts and usage.
busySet while chat input is waiting or processing, or an open task can still progress. The web client keeps polling while it is set.
versionChanges with anything those reads cover, including every lease renewal during a turn. It doesn't change for a finished task's late spend, or for usage records written outside a turn.
Session fetchThe client fetches the session on its first status call, when version changes, when a status call fails, and once when busy turns false.
Missing or failingIf the endpoint is missing, or a status call fails three times in a row, the web client polls the session every 2 seconds instead.

The protocol for many clients

designed · milestones 8 and 12

Once there's more than one client, polling gives way to an ordered event log.

Start from a snapshotGET /v1/snapshot returns the state and the log position it reflects.
↓
Follow the streamGET /v1/events sends saved events and resumes after a reconnect.
↓
Send commandsPOST /v1/commands returns once a command is saved.
Protocol details
CommandEffect
message.sendSaves the user's message and puts it in the inbox.
message.editSaves a new message that replaces the old one, treated as a correction.
task.stopRequests Stop. Skips classification.
approval.decideRecords approve or decline for one exact operation.
doc.updateEdits soul or memory, with conflict detection.
settings.updateChanges quiet hours, the daily cap and so on.
device.registerRegisters a device for push.

Replies arrive as typed parts: text, chips, image, artifact, approval and attachment. Each non-text part has fallback text, so an older client can still show something.

  • One log and one stream per owner, since tasks and badges span threads.
  • Server-sent events with a long-poll fallback. WebSockets were rejected for now because commands already use POST.
  • Clients don't read Firestore directly, so its schema doesn't become the contract.
  • Task results land in the thread that started the task.

Everything beyond today's API is a proposal.

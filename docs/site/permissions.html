What decides a call

Connecting an MCP server or account grants no execution authority on its own. Every call is evaluated by core/internal/permissions against the connection's granted scopes, the user's permission rules, the task's origin (direct user request vs. automation) and deployment defaults. Rules specify exact selectors—tool_ids, connection_ids, resource_ids, action_classes, optional recipients, automation_id, goal_id, expires_at and max_operations. Empty selector lists match nothing, explicit * wildcards match any, and deny always wins.

Action classExamplesDefault (no matching rule)
readSearch, MCP protocol reads, read-only lookupsAllowed when available/connected
reversible_writeDrafts or reversible state changesAllowed for direct user requests; asks for unattended automations
sensitive_sendOutbound messages, broadcasts or irreversible sendsFollows UserSends on direct requests (UnattendedWrites for automations)
unknownDiscovered MCP server tools (annotations are advisory)Always requires an approval card or an explicit matching allow rule

For unattended automation runs, UnattendedWrites defaults to confirm_writes (creates a pending approval interaction) or can be set to require_rule (denies writes unless an explicit allow rule matches).

Approvals stay bound to what they approve

An approval interaction records the task ID, instruction revision, interaction revision and exact action_digest. A steer to the task supersedes any open approval in the same transaction that advances the task revision. Submitting a stale decision returns HTTP 409 (revision_conflict or interaction_stale) with the current state, and an old digest can never match a modified action. Declining executes nothing and runs optional cleanup hooks.

After approval, the task re-invokes the call. The idempotency key comes from the task, its revision and the action digest—so an unchanged repeat consumes the approval once and reuses the same key: one approval, one write. Any changed parameter produces a new digest and requires a fresh approval.

The user's response, the interaction resolution, the mutation receipt and the command that resumes the task are committed together in Postgres. The host app and the workbench both respond through POST /v1/interactions/{id}/responses with { request_id, expected_revision, value: { kind: "approve" | "decline", action_digest } }.

Questions and other interactions

Task questions, account choices and approvals share the same typed interaction record under /v1/interactions: each carries a status, revision, typed payload and optimistic concurrency checks. Work surfaces every pending interaction so the host app or the workbench can render approval cards consistently.

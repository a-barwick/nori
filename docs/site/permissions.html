Permissions and approvals

Deny-wins permission rules and action-digest-bound approval cards decide whether a tool call may run, and ensure an old approval can never authorize a changed action.

What decides a call

Connecting an MCP server or account grants no execution authority on its own. core/internal/permissions evaluates every call against four inputs:

  • the connection's granted scopes
  • the user's permission rules
  • the task's origin, either a direct user request or an automation
  • deployment defaults

Rules use exact selectors: tool_ids, connection_ids, resource_ids, action_classes, and optionally recipients, automation_id, goal_id, expires_at and max_operations. An empty selector list matches nothing, an explicit * matches anything, and a deny rule always wins.

Action classExamplesDefault (no matching rule)
readSearch, MCP protocol reads, read-only lookupsAllowed when available/connected

sensitive_sendOutbound messages, broadcasts or irreversible sendsFollows UserSends on direct requests (UnattendedWrites for automations)
unknownDiscovered MCP server tools (annotations are advisory)Always requires an approval card or an explicit matching allow rule

For unattended automation runs, UnattendedWrites defaults to confirm_writes (creates a pending approval interaction) or can be set to require_rule (denies writes unless an explicit allow rule matches).

Approvals stay bound to what they approve

  • An approval interaction records the task ID, instruction revision, interaction revision and exact action_digest.
  • A steer to the task supersedes any open approval in the same transaction that advances the task revision.
  • A stale decision returns HTTP 409 (revision_conflict or interaction_stale) with the current state.
  • A changed parameter produces a new digest and needs a fresh approval, because an old digest never matches a modified action.
  • Declining executes nothing and runs optional cleanup hooks.
  • After approval, the task re-invokes the call with an idempotency key built from the task, its revision and the action digest. An unchanged repeat reuses the key and consumes the approval once, so one approval allows one write.

Postgres commits the user's response, the interaction resolution, the mutation receipt and the command that resumes the task together. The host app and the workbench both respond through POST /v1/interactions/{id}/responses with { request_id, expected_revision, value: { kind: "approve" | "decline", action_digest } }.

Questions and other interactions

Task questions, account choices and approvals share the same typed interaction record under /v1/interactions: each carries a status, revision, typed payload and optimistic concurrency checks. Work surfaces every pending interaction so the host app or the workbench can render approval cards consistently.

What decides a call

Installing a package or connecting an account grants nothing. Each call is checked against the account's granted scopes, the user's rules, the task's own instructions and the deployment's limits. Rules list exactly which tools, accounts, resources, action types and recipients they cover; an empty list covers nothing, and a deny always wins. A tool that does not declare a trusted effect is treated as unknown and needs explicit permission.

Whether an automation may send or write without asking is still the user's decision; until then it asks.

Approvals stay bound to what they approve

An approval names the task, its instruction revision and the action digest. A correction to the task supersedes the open approval in the same step that advances the revision, and the replacement shows the changed action. Approving the old one returns a conflict with the current state, and an old digest never matches the new action. Declining writes nothing.

After an approval, the task repeats the call. The idempotency key comes from the task, its revision and the action, not from the call, so an unchanged repeat matches the approval and reuses the same provider key: one approval, one write. A changed repeat is a different action and is asked about again.

The answer, the resolution and the command that resumes the task are saved together. If the answer arrives before the task is waiting for it, the command waits and is delivered when the task asks.

Questions, sign-in and takeover

Questions, account choices, sign-in requests and computer takeovers use the same interaction record: it has a revision, it expires, and a response must name the revision it answers. Work lists every open interaction under Needs you.

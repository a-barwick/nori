Tool discovery

How the inner loop will find and load only the tools a task needs.

Dynamic tool discovery designed · milestone 5

Today each loop has a fixed tool list: six for the outer loop, and up to five for the inner loop (complete, shell, browser_navigate, browser_screenshot and request_input). The plan is for the inner loop to start small and load only what a task needs, so adding connectors doesn't fill its context with tool schemas.

1. CatalogShort entries give each capability's purpose, account, scope, availability and failure behavior. AB-158
2. DiscoverThe inner loop looks for capabilities using the task, its evidence and the connected services. AB-159
3. LoadOnly the selected schemas enter the model's context. They can be cached until an account or tool changes. AB-160
4. Check and runThe runtime checks permission when the call runs. Finding or loading a tool never grants access. AB-168
  • The outer loop keeps its small set of coordination tools and a short summary of what the inner loop can do.
  • A disconnected or missing tool is reported as unavailable, so it can't be confused with a tool the model didn't select.
  • Still open: the catalog format, search and ranking, schema caching, and the first connector.

An example

What's on my calendar Thursday?

ConnectedThe call runs and the answer names the account.
Not connectedThe task says so and asks the user to connect it.

Rules that don't change

  • Picking a tool never grants permission.
  • Tool descriptions and tool output are data. Text inside them can't change the task or its permissions.
  • Discovery counts against the task's budget and stops when the task stops.
  • Small tasks shouldn't have to rediscover the same tool on every step.

Clients

If two clients could disagree about something, the service owns it. A client only owns how that looks on its own screen.

What a client never does

  • Build prompts or send context. It only sends Austin's own words and references.
  • Parse model output.
  • Assume a command has finished because it was accepted.
  • Talk to a model provider directly.

The API today

The web app sends commands and polls for snapshots: every 2 seconds while work is running, and every 30 seconds during long waits.

EndpointWhat it does
POST /api/sessionReturns the conversation and tasks.
POST /api/turnSends a message. Returns 202 once it's saved.
POST /api/commandSends a task command, such as an answer or a continue.
POST /api/inputSends an explicit update to one task.
POST /api/cancelRequests Stop for one task.
POST /api/traceReads the debug trace for a turn or task.
POST /api/artifactReads a saved file such as a screenshot.
POST /api/processThe wake from Cloud Tasks. Clients don't call it.
POST /api/resumeRedelivers saved commands and wakes tasks. Clients don't call it.

The protocol for many clients designed · milestones 8 and 12

Once there's more than one client, polling gives way to an ordered event log.

Start from a snapshotGET /v1/snapshot returns the state and the log position it reflects.
↓
Follow the streamGET /v1/events sends saved events plus live extras like reply text. A reconnect picks up from the last event.
↓
Send commandsPOST /v1/commands returns once a command is saved. Its effects arrive later as events.
Commands and message parts
CommandEffect
message.sendSaves Austin's message and puts it in the inbox.
message.editSaves a new message that replaces the old one, treated as a correction.
task.stopRequests Stop. Skips classification.
approval.decideRecords approve or decline for one exact operation.
doc.updateEdits soul or memory, with conflict detection.
settings.updateChanges quiet hours, the daily cap and so on.
device.registerRegisters a device for push.

Replies arrive as typed parts: text, chips, image, artifact, approval and attachment. Each non-text part has fallback text, so an older client can still show something.

Decisions in that proposal
  • One log and one stream per owner, since tasks and badges span threads.
  • Server-sent events with a long-poll fallback. WebSockets were rejected for now because commands already use POST.
  • Clients don't read Firestore directly, so its schema doesn't become the contract.
  • Task results land in the thread that started the task.

Inner loop

Each task calls a model, runs its tools and saves the results for the next step.

Task workflowReads commands in order and checks the shared budget before calling the model.
↓ “Check Saturday's weather in Tucson” and saved history
Inner modelReturns tool calls, a question, a work request or a completion proposal.
↓ proposed calls
RuntimeChecks the instructions and runs tools, saves a question or checks completion.
↓ tool call, when needed
Worker or computerRuns the tool and returns its result.
↓ tool result
RuntimeSaves results for the next step, or publishes the checked outcome after cleanup.
↺ saved results return to the task workflow

See Finishing a task for the checks, and Task lifecycle for the states.

When instructions change

  • A correction such as “No, Tucson” is saved as a command, and the loop reads it before the next model call.
  • If the instructions change before a tool call runs, that call gets a skipped result.
  • A call that already ran keeps its result, so every call has a paired result.

When something fails

OutcomeWhat the task does
A tool returns an errorThe model receives the error as a saved result.
A shell command fails after startingIf it may have changed something, later shell commands wait for the user's answer.
A write has an uncertain outcomeKeeps the operation record, then asks the user or reports an incomplete outcome. It doesn't repeat the write.
A model call's cost is unknownFails, so unpriced work never counts as free.
The task failsReports the failure, then waits for the user to start any new attempt.
Workflow details
  • Each task runs as one nori-task-v3 workflow.
  • The workflow body contains only deterministic transitions. Model calls, tools and writes to the store run as activities with timeouts.
  • Signals on task-command only wake the workflow. It then reads saved commands by position.
  • Model and tool activities have a 240-second timeout, and the model activity must heartbeat within 10 seconds. Stopping the computer has 200 seconds.
  • A browser tool that hits a transient error is retried once. A shell command with an uncertain outcome isn't repeated.
  • Shell commands run for up to 45 seconds in /workspace, capped by cgroups.
  • browser_navigate returns the title and visible text. browser_screenshot saves a PNG and gives the model a reference. The model reads it through a separate call.
  • An invalid tool batch sends per-call rejections back to the model, and nothing runs.
  • After 32 loops the workflow continues as a new run with the same task.
  • The workflow's spent figure is the one that counts. The copy in the task record can lag.
  • In request-driven mode, each Cloud Tasks wake runs a worker for up to 240 seconds and hands remaining work to the next wake. Parked tasks resume on a compatible pinned build.

See Tool authority for how the runtime handles uncertain operations.

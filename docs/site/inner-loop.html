Inner loop

Each task calls a model, runs built-in or MCP tools through the permission-checked executor and saves results for the next step.

Task workflowReads commands in order and checks the shared budget before calling the model.
↓ “Pull the latest Q3 revenue summary” and saved history
Inner modelReturns tool calls, a question, a work request or a completion proposal.
↓ proposed calls
RuntimeChecks instructions and permissions, runs tools, saves an interaction or checks completion.
↓ tool call, when needed
Tool executor & MCPRuns built-in runtime tools or calls connected MCP servers and returns evidence.
↓ tool result
RuntimeSaves results for the next step, or publishes the checked outcome after cleanup.
↺ saved results return to the task workflow

See Finishing a task for the checks, and Task lifecycle for the states.

When instructions change

  • A correction such as “Use Q2 instead” is saved as a command, and the loop reads it before the next model call.
  • If the instructions change before a tool call runs, that call gets a skipped result.
  • A call that already ran keeps its result, so every call has a paired result.

When something fails

OutcomeWhat the task does
A tool returns an errorThe model receives the error as a saved result.
A write has an uncertain outcomeKeeps the operation record, then asks the user or reports an incomplete outcome. It never repeats the write automatically.
A task reaches its spending budgetStops before the next model call and publishes an incomplete failed outcome with its saved work. There is no repeated continue budget question; the user can explicitly start a linked continuation task from Work.
A model call's cost is unknownRecords cost_status = unknown on the usage row and checkpoint without failing the response or invalidating a successful result.
The task failsReports the failure, then waits for the user to start any new attempt.
Runner details
  • Each task runs in task.Runner inside worker.Pool, holding a 30-second document-fenced lease on TaskControl renewed every 10 seconds.
  • Every model call, tool call and state transition persists its checkpoint directly in Postgres (TaskModelCheckpoint, OperationRecord and private history blocks) without requiring deterministic code replay.
  • New commands (steer, answer, stop, subtask_result) update nori_task_leases in the same transaction and emit NOTIFY nori_wake so a running or parked task reacts immediately.
  • Model and tool steps have a 240-second timeout; interrupted model calls reuse saved TaskModelCheckpoint receipts or retry up to twice within the 9-minute model step deadline without double-billing.
  • Tool definitions are pinned by content digest on each OperationRecord so approvals and audit evidence stay bound to the exact schema and arguments even when MCP servers update.
  • An invalid tool batch sends per-call rejections back to the model, and nothing runs.
  • TaskControl and Postgres hold the authoritative live spend and checkpoint state directly—there is no second workflow store to keep in sync.
  • cmd/nori --role=worker (or --role=all / nori-local) runs the unified Postgres-native worker pool for both inner tasks and outer conversation/scheduler lanes.

See Tool authority and Permissions and approvals for how the runtime guards writes and uncertain operations.

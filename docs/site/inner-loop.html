Inner loop

One loop per task: call the model, run the tools it asks for, save the results, repeat.

Each task gets one workflow (nori-task-v2).

  • The workflow body in task/workflow.go contains only deterministic transitions.
  • Every model call, tool call and Firestore write is an activity with its own timeout.
  • Signals (task-command) only wake the workflow. It then reads commands from Firestore by position and incorporates each one exactly once.

Plain text answerStops the computer if it was used, runs the Publish activity with a revision check, and ends the workflow. This is how tasks complete today.

Deferred finish() on every exitRuns on a disconnected context. It projects final spend, confirms the computer stopped (Stop activity, 200s), and publishes failed or cancelled along with any effects so far. If the workflow can't confirm the computer stopped, it doesn't report success.

  • The worker uses pinned deployment versions (TEMPORAL_BUILD_ID per release), and parked tasks resume on a compatible version.

  • In request-driven mode, each Cloud Tasks wake runs a worker for one bounded slice of up to 240s and hands remaining work to the next wake.

When a tool fails

Today a nonzero shell exit reaches the model, but a transport error ends the task. The plan is for every error to come back as a tool result, with retries set by what the tool does.designed

Tool typeTemporary failureOutcome unknown
ReadRuntime retries within limits.Safe to retry.
Reversible writeRetry only with the same operation ID and duplicate protection.Check the provider before any repeat.
Sensitive send or purchaseAsk the user first.Check safely, then ask the user.
How other systems deliver mid-run input

Nori collects steers at tool boundaries, and the runtime owns the timing.

Memory and context

Nori couples a 3-tier memory architecture with pre-compaction flushing: no conversational context is compacted or retired until its durable facts commit to Memory, while live outer replies stay fast, KV-cache-stable, and prompt-injection-safe under 128 KiB.

Three-tier memory model

Canonical memory records live in 32-way owner-sharded nori_records JSONB documents, paired with an isolated full-text search index.

Layer 1 · Core Memoryowners/<o>/memories/<id> · ≤ 24 KiB total, ≤ 2000 B/item. Always injected at prompt index 1. Unpinned growth past 24 KiB auto-demotes the oldest unpinned items to today's Daily Log while protecting Pinned items — never failing with memory-full.
Layer 2 · Daily Episodic Logsowners/<o>/memory_logs/YYYY-MM-DD · ≤ 64 KiB / 128 entries per shard (auto-sharding to YYYY-MM-DD#2). Stores session decisions, pre-compaction notes, demoted Core facts, evicted summary items, and bounded (≤ 600 B) task_outcome takeaways.
Layer 3 · Working Memoryowners/<o>/conversation/summary · ≤ 16 KiB, 80 items, 4000 B gist. Tracks ExtractedThrough (EffectiveFlushedThrough ≤ EffectiveExtractedThrough) and FlushedThrough ≤ Through, quote-verified SummaryItems, dismissed IDs, and temporary Excerpts during rapid bursts.
  • Every Core memory and Daily Log entry carries explicit Provenance: user_explicit, pre_compact_flush, summary_evicted, task_outcome, or dream_curated.
  • Provenance & injection shield: A memory never grants tool permissions. Completed tasks append a bounded (≤ 600 B) task_outcome note to today's Daily Log in the same Publish transaction and never mutate Core Memory.
  • Two-call command guard: When a user turn mixes dispatch/steer with remember/forget — or coalesces with untrusted background task output — planUserCommands evaluates all four tools against user-only messages instead of dropping memory changes.
  • Atomic turn commits: Explicit remember/forget changes commit in the same transaction as the published reply, so retries apply them once and superseded replies apply none.

Postgres FTS index & tail auto-recall

To keep nori_records HOT-update-friendly and avoid SIREAD lock escalation, search lives in a dedicated 32-way hash-partitioned table nori_memory_chunks updated inside the same transaction and queried in READ COMMITTED READ ONLY (< 2 ms).

  • Dual-dictionary indexing: Stored GIN tsvector combines english stemming with simple tokenization so exact identifiers, UUIDs, emails, and code symbols match alongside natural language.
  • Decay & diversity ranking: Cover-density ts_rank_cd (plus exact-token boost) is weighted by 1.15 for pinned Core, 1.0 evergreen for Core, and a 30-day half-life recency decay 2^(-age_days/30) for Daily Logs, then reranked with deterministic token-Jaccard MMR (λ = 0.75) over top 32 candidates into ≤ 700-byte UTF-8 snippets tie-broken by chunk_id ASC.
  • Tail auto-recall: On user turns, the outer loop queries SearchMemory(Layer="log", TopK=8, CreatedAfter=ContextFrom) and appends matching snippets (≤ 4 KiB) to the tail advisory message so the static prompt prefix stays cached.

Inner-loop recall tools

Background tasks run with a 128 KiB transcript budget (fitContext omitting older tool outputs ≥ 512 B with operation_id stubs, then projectContext archiving older rounds behind history_ref). Default read tools give tasks direct, ContextFrom-isolated recall without granting permissions:

ToolReturns
memory_readCore Memory items and current Working Memory ConversationSummary (matching ContextFrom).
memory_searchRanked ≤ 700 B snippets across Core Memory and Daily Logs (layer filter, limit 1–20, strictly ≥ ContextFrom).
memory_getFull Core Memory (target: "core") or a specific YYYY-MM-DD Daily Log / entry_id (target: "log", strictly ≥ ContextFrom).
conversation_find / conversation_readMatches and full reads of earlier chat messages strictly ≥ ContextFrom.
operation_read / task_history_readSaved full outputs for fitContext-omitted tool calls and paginated transcript fragments for projectContext archives.

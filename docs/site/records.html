Records and delivery

What gets saved, where, and how a saved command reaches Temporal.

Records are small and explicit, with stable IDs. Firestore and Temporal can't share a transaction, so a relay connects them:

  • Acceptance is a Firestore commit.
  • Delivery is retried until it's acknowledged.
  • Consumers deduplicate by ID and position.

Firestore layout database nori-poc

system/control            ← project pause switch
owners/{owner}/
├─ conversation/control   ← lease, fence, consumed
├─ conversation_inputs/   ← durable inbox (ordered)
├─ conversation_turns/    ← captured batches
├─ conversation_attempts/ ← traces: model, hint, usage
├─ messages/              ← the visible messages
├─ runs/{taskId}          ← task projection
│   ├─ history/           ← the task transcript, in blocks
│   ├─ steps/             ← per-activity traces
│   └─ operations/        ← admission receipts
├─ task_commands/         ← delivery intent → Temporal
└─ model_usage/           ← pre-recorded provider calls

Cloud Storage holds binaries, which today means screenshots at artifacts/{run}/{id}.png. Large transcripts and outputs stay out of workflow history, and workflows carry references to them.

The cross-service relay

AcceptThe command, run and delivery intent are saved in one Firestore transaction.
↓
Delivertask.Deliver starts workflow nori-task-{id} or sends the task-command signal. It retries on every process cycle and worker startup.
↓
AcknowledgeMarks the command as delivered. If the process crashes before this step, the command is delivered again, and positions make that harmless.

What happens when something dies

InterruptionRecovery
The outer process dies after accepting inputReclaim the saved turn and pending wake, with the original input ID.
The outer process dies around a dispatchRecover the saved model response and command receipts before accepting anything again.
A task command is delivered twiceRecognize its ID and position, and don't apply it again.
A worker restarts while a task waitsResume the same task and question on a compatible worker version.
A provider's response is lost after a writeReconcile the outcome before any retry.designed
The result is saved, then the client disconnectsReopen the saved result, and don't repeat the work.
A task crashes before it can reportThe runtime emits a failure event with completed and unresolved operations.
What each record has to hold
RecordHolds
Conversation inputStable ID, original content or event, accepted order, origin and processing state.
Outer turn attemptInput boundary, attempt ID, lease, model response, tool pairs, dispatch receipts, usage and publication state.
TaskStable ID, request, ordered instructions, incorporated position, revision, lifecycle, wait reason, budget and result references.
Command or eventStable ID, target, kind, order, revision, payload and delivery state.

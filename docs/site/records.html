Records and delivery

What gets saved, where, and how a saved command reaches Temporal.

Saved record layout

system/control            ← project pause switch
owners/{owner}/
├─ conversation/control   ← which turn holds it, what it has processed
├─ conversation_inputs/   ← durable inbox (ordered)
├─ conversation_turns/    ← captured batches
├─ conversation_attempts/ ← traces: model, hint, usage
├─ conversation/summary  ← earlier turns, with source quotes
├─ memories/              ← facts and preferences the user asked to save
├─ messages/              ← the visible messages, as typed parts
├─ events/                ← the ordered event log
├─ event_head/            ← the log's newest number
├─ uploads/               ← attached files' records
├─ results/               ← saved results
├─ runs/{taskId}          ← copy of task status
│   ├─ history/           ← the task transcript, in blocks
│   ├─ steps/             ← per-activity traces
│   └─ operations/        ← tool call records
├─ task_commands/         ← commands waiting to reach Temporal
└─ model_usage/           ← provider calls, saved first

Cloud Storage holds binaries under artifacts/: screenshots, attached files and saved files. Large transcripts and outputs stay out of workflow history, and workflows carry references to them.

Who owns what

QuestionAnswer lives in
Was it accepted?Database command record
What has the task spent?Workflow state (the database holds a copy)
Which instructions are current?Commands the task has already read
Did that tool call happen?Operation record and the computer's receipt
What did the models cost?model_usage, written before each call

The database and Temporal can't share a transaction, so a relay delivers saved commands. Consumers ignore repeats by ID and position.

What happens when something dies

InterruptionRecovery
The outer process dies after accepting inputReclaim the saved turn and pending wake, with the original input ID.
The outer process dies around a dispatchRecover the saved model response and command receipts before accepting anything again.
A task command is delivered twiceRecognize its ID and position, and don't apply it again.
A worker restarts while a task waitsResume the same task and question on a worker build that can run it.
A provider's response is lost after a writeRead the provider's record before considering another action. An attempted operation cannot send again.
The result is saved, then the client disconnectsReopen the saved result, and don't repeat the work.
A task crashes before it can reportThe runtime emits a failure event with completed and unresolved operations.

Storage layers

Each layer is a Go package in the service's internal folder.

LayerCodeJob
Records and rulesstate/The record types, errors and store contracts, and the rules that decide whether a write is allowed, such as accepting commands, checking revisions and leases, and publishing results.
Persistencestate/records/Applies the rules inside transactions. Shared by both backends, including leases, write claims, recovery and event numbering.
Document backendsstate/firestore/ and state/postgres/Implement the narrow transaction and query contract in state/docstore/. Firestore paths and saved field names stay unchanged; Postgres stores the same records as indexed JSONB.
File bytesstate/gcs/, state/s3/ and state/localfs/Stores screenshots, attached files and saved files in Cloud Storage, S3 on AWS, or a private folder for local runs.
Model usageusage/Records model calls in the selected database, optionally also reporting to a host. The workflow enforces the task spending ceiling.
Wiringplatform/Selects NORI_STORE_BACKEND: Firestore by default, or Postgres with NORI_POSTGRES_URL. Firestore requires NORI_PROJECT_ID and FIRESTORE_DATABASE_ID.

Postgres applies numbered SQL migrations at startup under a transaction lock. Serializable transactions update each event head with its records, so aborted writes do not consume event numbers. Event streams poll committed records every 250 ms in batches of 200, resuming after the last delivered sequence. This keeps reconnects independent of notifications and releases database connections between polls. Firestore keeps its snapshot listeners.

make deps starts local Postgres and Temporal. See local setup. Switching backends does not migrate existing data. Files use Cloud Storage, S3 or a local folder, selected by NORI_CLOUD.

A different database or object store needs its own adapter for these contracts. The rules stay in state; shared persistence lives in state/records.

What each record has to hold
RecordHolds
Conversation inputStable ID, original content or event, accepted order, origin and processing state.
Outer turn attemptInput boundary, attempt ID, lease, model response, tool pairs, dispatch receipts, usage and publication state.
TaskStable ID, request, ordered instructions, incorporated position, revision, lifecycle, wait reason, budget, result references, and its parent or subtasks.
Command or eventStable ID, target, kind, order, revision, payload and delivery state.
OperationStable ID, parameters, attempt state, confirmation or uncertainty, and evidence.
Saved resultStable ID, task link, file details, version and delivery times.
Write claimThe operation holds the exact saved action and its digest. One transaction changes ready to attempted before sending; uncertain outcomes remain available for recovery.

Records and delivery

What Nori saves in Postgres and in file storage, and how leases and wakes in Postgres coordinate work.

Saved record layout

system/control            ← execution pause switch
nori_task_leases          ← runnable/parked task discovery table
nori_user_wakes           ← due conversation & scheduler wakes
nori_sequences            ← 32-way hash-partitioned event sequences
nori_memory_chunks        ← indexed FTS memory chunks
owners/{owner}/
├─ conversation/control   ← active lease, fence, consumed position
├─ conversation_inputs/   ← durable inbox (ordered)
├─ conversation_turns/    ← captured batches
├─ conversation_attempts/ ← traces: model, hint, usage
├─ conversation/summary   ← compacted older turns, with source quotes
├─ memories/              ← Core & working memory items
├─ memory_logs/           ← dated daily memory logs
├─ messages/              ← visible messages, as typed parts
├─ events/                ← ordered event log
├─ event_head/            ← log's newest sequence number (fallback)
├─ uploads/               ← attached file metadata
├─ results/               ← saved versioned results
├─ resources/             ← connections, MCP servers, rules,
│                           interactions, automations, goals, inbox
├─ credentials/           ← envelope-encrypted secrets (rowstore)
├─ runs/{taskId}          ← task status & budget projection
│   ├─ control            ← TaskControl lease, fence & checkpoint
│   ├─ history/           ← task transcript, in blocks
│   ├─ steps/             ← per-step traces & model checkpoints
│   └─ operations/        ← tool call records & evidence
├─ task_commands/         ← ordered commands for each task
└─ model_usage/           ← provider calls, saved before dispatch

File bytes go to private object storage (S3, Google Cloud Storage, or a local folder in development) under artifacts/ with a prefix for each user.

Who owns what

QuestionAnswer lives in
Was it accepted?Postgres command record
What has the task spent?TaskControl and runs/{id} in Postgres
Which instructions are current?Commands the task has already read by position
Did that tool call happen?Operation record & provider evidence
What did the models cost?model_usage, written before each call

Commands, checkpoints, leases and wakes share the same Postgres transactions. Consumers ignore repeats by ID and position.

What happens when something dies

InterruptionRecovery
The outer process dies after accepting inputReclaim the saved turn and pending wake, with the original input ID.
The outer process dies around a dispatchRecover the saved model response and command receipts before accepting anything again.
A task command is delivered twiceRecognize its ID and position, and don't apply it again.
A worker restarts while a task waitsResume the same task and open question or approval on a compatible worker build.
A provider's response is lost after a writeRead the provider's record before considering another action. An attempted operation cannot send again.
The result is saved, then the client disconnectsReopen the saved result and resume the SSE stream from the last sequence number.
A task crashes before it can reportThe runtime emits a failure event with completed and unresolved operations.

Storage layers

LayerCodeJob
Records and rulescore/internal/state/Record types, store contracts and write rules for commands, revisions, leases and results.
Persistencecore/internal/state/records/Applies the rules inside transactions, including leases, write claims, recovery and event numbering.
Document storecore/internal/state/docstore/ and core/internal/state/postgres/Implements the transaction and query contract on indexed JSONB tables, with numbered SQL migrations.
File bytescore/internal/state/s3/, core/internal/state/gcs/ and core/internal/state/localfs/Saves uploaded files and result bytes, with conditional writes that refuse overwrites on the cloud stores.
Encrypted credentialscore/internal/secret/rowstore/Saves per-user MCP and connection secrets in Postgres with envelope encryption.
Wiringcore/internal/platform/Picks adapters from NORI_CLOUD.
  • Postgres applies numbered SQL migrations at startup under a transaction lock.
  • Serializable transactions update each event sequence together with its records, so an aborted write never uses an event number.
  • SSE streams share one LISTEN nori_watch hub per process. A 20-second fallback poll covers missed notifications, and each stream resumes after the last sequence number it delivered.
What each record has to hold
RecordHolds
Conversation inputStable ID, original content or event, accepted order, origin and processing state.
Outer turn attemptInput boundary, attempt ID, lease, model response, tool pairs, dispatch receipts, usage and publication state.
TaskStable ID, request, ordered instructions, incorporated position, revision, lifecycle, wait reason, budget, result references, and its parent or subtasks.
Command or eventStable ID, target, kind, order, revision, payload and delivery state.
OperationStable ID, parameters, pinned tool digest, attempt state, confirmation or uncertainty, and provider evidence.
Write claimThe operation holds the exact saved action and its digest. One transaction changes ready to attempted before sending, and uncertain outcomes stay available for recovery.

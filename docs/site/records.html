Records and delivery

What gets saved, where, and how a saved command reaches Temporal.

Records are small and explicit, with stable IDs. Firestore and Temporal can't share a transaction, so a relay connects them:

  • Acceptance is a Firestore commit.
  • Delivery is retried until it's acknowledged.
  • Consumers deduplicate by ID and position.

Firestore layout database nori-poc

system/control            ← project pause switch
owners/{owner}/
├─ conversation/control   ← lease, fence, consumed
├─ conversation_inputs/   ← durable inbox (ordered)
├─ conversation_turns/    ← captured batches
├─ conversation_attempts/ ← traces: model, hint, usage
├─ messages/              ← the visible transcript
├─ runs/{taskId}          ← task projection
│   ├─ steps/             ← per-activity traces
│   └─ operations/        ← admission receipts
├─ task_commands/         ← delivery intent → Temporal
└─ model_usage/           ← pre-recorded provider calls

Cloud Storage holds binaries, which today means screenshots at artifacts/{run}/{id}.png. Large transcripts and outputs stay out of workflow history, and workflows carry references to them.

The cross-service relay

AcceptThe command, run and delivery intent are saved in one Firestore transaction.
↓
Delivertask.Deliver starts workflow nori-task-{id} or sends the task-command signal. It retries on every process cycle and worker startup.
↓
AcknowledgeMarks the command as delivered. If the process crashes before this step, the command is delivered again, and positions make that harmless.

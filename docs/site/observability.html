Observability

Each Nori process records traces, errors, logs and metrics, and exports them to Sentry and Arize when configured.

Client / host appStarts when the user sends a message.
↓ traceparent header
Host / web serverBuilds new trace headers and forwards no untrusted browser headers.
↓ traceparent header
Agent service (nori)Saves the traceparent with the input in Postgres alongside the durable wake row.
↓ saved traceparent
Outer loopContinues the saved trace, and dispatches carry it onto each task.
↓ saved traceparent
Inner loop (task.Runner)Each task step reads the traceparent from the task and traces model and MCP tool calls.

What's removed before export

DataWhat's sent
Span and log attributesAllowlisted names only. Strings are cut to 256 bytes after redaction.
ErrorsA category, a fixed reason such as deadline or http_503, the error type and a stack without variables or source lines. Error text is dropped.
HTTP requestsMethod, known route and status. URLs, headers and bodies are dropped.
Model text in ArizeThe latest user message and the reply, up to 2,048 bytes each. URLs, email addresses, tokens and known credentials are replaced with [redacted].
Tool callsTool name, outcome and status. Arguments and tool payloads are not on the allowlist.
Browser eventsSent to /sentry-tunnel, which checks authentication and strips request headers before forwarding.

Sampling and failures

  • The browser and each Go process sample 5% of new traces by default.
  • Each export has a 2-second timeout and no retries.
  • A failed export writes one line to stderr, at most once a minute.

Diagnostics and feedback

GET /v1/diagnostics lists per-user problems that need repair: a task stuck behind an undelivered answer, a write with an uncertain outcome, cleanup that did not finish, a missed wake, a failed delivery, or a connection or MCP server that needs attention. Each item names its task, operation or resource and, when a repair exists, runs it through POST /v1/diagnostics/actions using the same durable records and commands as normal work.

Feedback (wrong result, wrong action, too slow, missing capability, broken connection) is saved via POST /v1/feedback with the task's operations, status and spend so issues point directly at recorded evidence.

How the loops talk

The outer loop sends commands in, and tasks send events back. Nothing else crosses between them.

For “Check Saturday's weather in Tucson”, the outer loop calls dispatch, which saves a start command. “No, Phoenix” becomes a steer on that task. When the forecast is saved, the task sends a result event.

The rules

  • Only the outer loop starts tasks. This stops tasks from spawning more tasks on their own.
  • One task, one ID. The start command's ID is the task ID, and every later command and event uses it.
  • Finished tasks stay finished. More work means a new task.
  • Accepted comes before applied. A command is saved first, and the task picks it up later.
  • Buttons skip the models. The Stop button and task panel edits send the same commands directly.
  • New work never gets more permission than the request it serves. A subtask's writes still need approval.

Outer loop tools

ToolWhen it's used
dispatch(request, for, question_id, attachments, revises)Start new work or a subtask, with any earlier files or a result to revise.
steer(run_id, text, interrupt)Change an unfinished task.
answer(run_id, question_id, text)Answer that task's open question.
continue(run_id, question_id)Add budget, only after the user says to keep going.
approve(run_id, question_id), decline(run_id, question_id)Decide one exact action from the user's message.
stop(run_id)Stop one task and its subtasks.
hold(task_id, question)Answer one of the user's questions when that task's result arrives.
show_result(result_id)Show a saved result with no task.

A plain reply is just text, with no tool call.

Inner loop control tools

Each must be the only call in its response.

ToolWhat it does
request_input(question)Save a question and wait for its exact answer.
complete(answer, evidence, unmet)Propose that the task is done. The checks decide.
request_work(request, why)Ask for work outside this task's own request, and wait. A subtask doesn't have this tool.

Events

Each event goes into the conversation inbox in the same transaction as the task's new state, then starts an outer turn. A subtask ending while its parent waits sends no event, unless it has a held question.

EventWhen it's sent
needs_inputThe task has a question, has a work request, or reached its budget.
resultThe task finished.
failureThe task ended without finishing.
stoppedThe task stopped after a Stop request.

Subtasks

A calendar task told to stay on the calendar can't look up Saturday's forecast itself, so it asks.

↓ work request
Outer loop turnDispatches a subtask, answers the request, or asks the user.
↓ start command
Subtask B runsIf B needs the user, it asks directly. A keeps waiting.
↓ B's outcome
RuntimeSaves B's outcome as the result of A's call, with no outer turn.
  • Budget: B's cost counts against A's budget.
  • Stop: A ending for any reason stops B. A correction to A also stops B and closes the request.
Subtask limits
  • A turn with a work request and no user message can only settle that request. It can't approve, continue, stop or steer.
  • One request can start up to 4 subtasks, all in one outer response. Their results arrive together when the last one ends.
  • A subtask can't start its own subtasks.
  • A pause holds a saved result until execution resumes.

The parent-waits-for-children pattern comes from job queues. The outcome and the command that delivers it are saved in one transaction. The rejected options are on Decisions.

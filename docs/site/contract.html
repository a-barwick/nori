How the loops talk

The outer loop sends commands in. Tasks send events back. Nothing else crosses between them. Open Data on a row to see what's sent.

The rules

  • Only the outer loop starts tasks. This stops tasks from spawning more tasks on their own.
  • One task, one ID. The start command's ID is the task ID, and every later command and event uses it.
  • Finished tasks stay finished. More work means a new task.
  • Accepted comes before applied. A command is saved first, and the task picks it up later.
  • Buttons skip the models. Stop and panel edits send the same commands directly.
  • New work never gets more permission than the request it serves.

Outer loop tools

ToolWhen it's used
dispatch(request)Start new work.
steer(task, text)Change an unfinished task.
answer(task, question, text)Answer that task's open question.
continue(task, question)Add budget, only after the user says to keep going.
stop(task)Stop one task.
hold(task, question)Answer one of the user's questions when that task's result arrives.designed

A plain reply or clarifying question is just text, with no tool call.

Inner loop control tools

These sit next to the task's work tools, and each must be the only call in its response.

ToolWhat it does
wait_for_input(question)Ask the user something. This is today's version.
request_input(question)Replaces wait_for_input.designed
complete(answer, evidence, unmet)Propose that the task is done. The checks decide.designed
request_work(request, why)Ask for work outside this task's own request.designed

Events

Each event goes into the conversation inbox in the same transaction as the task's new state, then starts an outer turn.

EventWhen it's sent
needs_inputThe task has a question, or it reached its budget.
resultThe task finished.
failureThe task ended without finishing.
stoppedThe task stopped after a Stop request.

Subtasks designed · milestone 7

A task sometimes needs work outside its request. It can't start that work itself, so it asks.

Task A calls request_workA parks and the question goes to the outer loop.
↓
Outer loop decidesDispatch a subtask, answer directly, or ask the user.
↓
Subtask B runs like any taskIf B needs the user, it asks the user itself. A keeps waiting.
↓
B's result goes back to ASaved in the same transaction as B's outcome. No model call is spent delivering it.
  • Budget: B's cost counts against A.
  • Stop: stopping A stops B.
  • Permissions: B never gets more than A has.
Why it's built this way

It's the standard parent-waits-for-children pattern from job queues, built on the outbox Nori already uses for commands. Agent frameworks tend to wait inside a single run, which doesn't cover parking a parent for hours across restarts. The rejected options are on Decisions.

Interrupting a task designed

A steer normally waits for the current step to finish. The outer loop can ask to cut the step short, and the runtime decides whether that's safe.

Can be cut shortA running model call, or a read such as loading a page. Stopping only loses time.
Runs to the endA write such as sending an email, which may already have happened. Shell and browser actions count as writes unless declared read-only.

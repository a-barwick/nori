How the loops talk

The outer loop sends commands to tasks. Tasks send events back with their saved outcomes.

Outer loop
↓ commands · ↑ events
RuntimeAssigns IDs and revisions, validates calls and saves commands and events.
↓ commands · ↑ events
Inner loop
  • For “Pull Q3 revenue summary”, the outer loop calls dispatch, which saves a start command.
  • “Include EMEA breakdown” becomes a steer on that task.
  • When the report is saved, the task sends a result event.

The rules

  • Only the outer loop dispatches work. A task can request a subtask through the outer loop.
  • Each task keeps one ID. Every command and event names its task.
  • Finished tasks stay finished. More work starts a new task.
  • Accepted comes before applied. A command is saved in Postgres first, and the task picks it up later.
  • Direct controls skip the models. Stop buttons, approval cards and task panel updates send commands directly.
  • Subtasks inherit their parent's authority. The runtime can limit one to reads.

Outer loop tools

ToolWhen it's used
dispatch(request, for, question_id, attachments, revises)Start new work or a subtask, with any earlier files or a result to revise.
steer(run_id, text, interrupt)Change an unfinished task.
answer(run_id, question_id, text)Answer that task's open question.
stop(run_id)Stop one task and its subtasks.
hold(task_id, question)Hold a question until that task's result arrives.
show_result(result_id)Show a saved result without starting a task.
remember(text, about, section, replaces), forget(memory_id)Save, update or delete an explicit memory.

There is no continue tool. A task that hits its budget stops incomplete, and Work can continue it as a linked new task.

Inner loop control tools

Each must be the only call in its response.

ToolWhat it does
request_input(question)Save a question and wait for its answer.
complete(answer, evidence, unmet)Propose that the task is done. The checks decide.
request_work(request, why)Ask for work outside this task's own request, and wait. A subtask doesn't have this tool.

Events

Task events enter the conversation inbox with the task's new state. Subtask outcomes go to waiting parents, unless a held question needs a reply.

EventWhen it's sent
needs_inputThe task has a question, needs a typed approval interaction, or has a work request.
resultThe task finished and passed completion checks.
failureThe task ended without finishing (including reaching its spending budget).
stoppedThe task stopped after a Stop request.

↓ B's outcome
RuntimeSaves B's outcome as A's call result, with no outer turn.
  • Budget: B's cost counts against A's budget.
  • Stop: A ending for any reason stops B. A correction to A also stops B and closes the request.
Work request results and limits
ResultHow the parent uses it
Direct answerThe result has answer and question_id, without an operation ID.
Subtask resultThe result lists each subtask's status, answer and unmet items. The parent cites its operation_id.
  • A turn with a work request and no user message can only dispatch work, answer the request or ask the user.
  • One request can start up to 4 subtasks, all in one outer response. Their results arrive together when the last one ends.
  • A subtask can't start its own subtasks.

The outcome and the command that delivers it are saved in one transaction. The rejected options are on Decisions.

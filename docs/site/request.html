Following a request

One message, “Check Saturday's weather in Tucson. Also find a time for dinner.”, followed from send to result.

1
The user sends a message with a stable UUIDaccepted
  • The agent service saves the input to the Firestore inbox and schedules a wake, then returns 202.
  • Retrying with the same UUID does nothing.
2
An outer turn claims the batch
  • A Cloud Tasks wake starts the turn, or the local loop in development.
  • The turn claims the conversation, so only it can write, and takes the next pending inputs in order.
  • A follow-up during the turn restarts it with all the inputs, up to 3 times.
3
Jev adds a hint and the outer model replies
  • Jev marks which intents are present. The hint grants no permission. See Classifying a message.
  • The outer model receives the history, task records and hint. It returns a reply and two dispatches.
  • The usage row is written before the provider call, so a crash can't lose a billed request.
4
Commands are validated together, then acceptedapplied (later)
  • Every command in the batch is validated before any of them is accepted.
  • Each dispatch becomes a start command whose ID is also the task ID.
  • The reply is published in the same transaction that consumes the inbox batch.
5
The relay starts one Temporal workflow per task
  • The runtime's relay, which delivers saved commands, starts a nori-task-v3 workflow or signals one that exists.
  • A signal only wakes the workflow. Firestore holds the ordered commands.
  • The weather and dinner tasks now run independently.
6
Inner loops work, wait and finishcompleted
  • Each task calls its model, runs tools on the computer and saves the results.
  • A message like “after seven” steers only the dinner task.
  • A task that needs an answer waits and starts an outer turn, while the other task carries on.
  • Record checks decide whether a task can finish. See Finishing a task.
7
The result comes back as a conversation event
  • The saved result goes into the same inbox as a task notification.
  • An outer turn without task tools explains it to the user.
  • If new user input is waiting, publication holds until that input has been routed.

At each handoff, Nori saves a record first and sends the notification afterwards. Data shows what each step sends.

Follow-ups and controls

InputWhat should happen
“Did you send it?”Answer from the receipt, or dispatch a check. Never send it again.
“Check that appointment again”Steer the open task, or start a new task if it has finished.
“Stop that”Resolve which task is meant, and ask if it's unclear. The Stop button already has a target.
The browser closesTasks keep running.
The backend restartsResume from saved state, and check uncertain outcomes before any retry.

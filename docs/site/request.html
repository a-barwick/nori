Following a request

One message, “Pull the latest Q3 revenue summary. Also draft a launch brief.”, followed from send to result.

1
The user sends a message with a stable UUIDaccepted
  • The agent service saves the input to the Postgres inbox and enqueues a wake, then returns 202.
  • Retrying with the same UUID is idempotent.
2
An outer turn claims the batch
  • A Postgres wake in nori_user_wakes (prompted by NOTIFY nori_wake or the 2-second poll) starts the turn in worker.Pool.
  • The turn claims the conversation lease and fence, so only it can write, and takes the next pending inputs in order.
  • A follow-up during the turn restarts it with all the inputs, up to 3 times.
3
Jev adds a hint and the outer model replies
  • Jev marks which intents are present. The hint grants no permission. See Classifying a message.
  • The outer model receives history, task records and the hint, returning a reply and two dispatches. An independent second call checks dispatches against user messages only.
  • The usage row is written before the provider call, so a crash can't lose a billed request.
4
Commands are validated together, then acceptedapplied (later)
  • Every command in the batch is validated before any of them is accepted.
  • Each dispatch becomes a start command whose ID is also the task ID, and inserts a runnable row in nori_task_leases in the same transaction.
  • The reply is published in the same Postgres transaction that consumes the inbox batch.
5
The worker pool claims each task lease
  • NOTIFY nori_wake wakes worker pods, which claim due rows from nori_task_leases and acquire the document-fenced TaskControl lease.
  • New commands update nori_task_leases transactionally, and the runner reads saved commands by position from Postgres.
  • The revenue and brief tasks now run independently.
6
Inner loops work, wait and finishcompleted
  • Each task calls its model, runs built-in or MCP tools through the permission-checked executor and saves the results.
  • A follow-up like “keep the brief under one page” steers only the brief task.
  • A task that needs an answer or approval waits and emits an interaction, while the other task carries on.
  • Record checks decide whether a task can finish. See Finishing a task.
7
The result comes back as a conversation event
  • The saved result enters the same inbox as a task notification.
  • An outer turn without task tools compares the answer against cited evidence and explains it to the user.
  • If new user input is waiting, publication holds until that input has been routed.

At each handoff, Nori saves a record first and sends the notification afterwards. Click Data on any step to inspect the payloads.

Follow-ups and controls

InputWhat should happen
“Did you send it?”Answer from the saved operation receipt, or dispatch a read check. Never repeat the write.
“Check those numbers again”Steer the open task, or start a new task if it has finished.
“Stop that”Resolve which task is meant, and ask if it's unclear. The Stop button already names its target.
The browser closesTasks keep running on Nori worker pods.
The backend restartsResume from saved Postgres state, and check uncertain outcomes before any retry.

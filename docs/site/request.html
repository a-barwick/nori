Following a request

Scroll through one message from send to result. The map shows which systems each step uses, and Data shows what they send.

Take this message: “Check Saturday's weather in Tucson. Also find a time for dinner.” That's two independent tasks in one conversation. At each handoff below, Nori saves a durable record first and sends the notification afterwards.

1
The user sends a message with a stable UUIDaccepted
  • POST /api/turn writes the input to the Firestore inbox in the same transaction as the user message.
  • The API returns 202 only once the save and the wake scheduling are both confirmed.
  • Retrying with the same UUID does nothing. Sending the same UUID with different text returns a 409.
  • From this point the browser can close.
2
An outer turn claims the batch
  • The local loop (every 2 seconds) or a Cloud Tasks wake starts Process.
  • Process acquires the conversation lease with a fence token and takes everything pending, in the order it was accepted.
  • Follow-up messages that arrive during the turn are saved and wait their turn, and the sender never gets a busy error.
3
Jev classifies and the model decides
  • Jev marks which intents are present. This is only a hint and doesn't grant permission for anything.
  • The outer model receives the history, the task records and the hint. It then replies in chat, dispatches the two tasks in one response, or does both.
  • Its usage row is written before the provider call, so a crash can't lose track of a request we were billed for.
4
Commands are validated together, then acceptedapplied (later)
  • Every tool call in the batch is validated before any of them is accepted.
  • Each dispatch becomes a start command whose ID is also the task ID for the life of the task. It's saved with its run record and delivery intent in one transaction.
  • After a final check for newer input, the reply is published in the same transaction that consumes the inbox batch.
5
The relay starts one Temporal workflow per task
  • The delivery relay starts nori-task-v2, or signals a workflow that already exists.
  • A signal is only a wakeup, because the positions in Firestore are authoritative.
  • The user has already received the acknowledgment by now, and the weather and dinner tasks run independently.
6
Inner loops work, wait and finishcompleted
  • Each task reads the instructions it has incorporated, calls its model, runs admitted tool operations on the computer, and saves the matching results.
  • A message like “after seven” steers only the dinner task.
  • If a task needs to ask for a location, it parks and starts an outer turn while the other task carries on.
  • Today a task completes when the model gives a final answer with no tool calls and that answer passes a revision recheck before publication.
7
The result comes back as a conversation event
  • The saved result goes into the same durable inbox as a task notification.
  • An outer turn without task tools explains it to the user.
  • If new user input is waiting, publication holds until that input has been routed, so a result can't get ahead of a correction that's still pending.

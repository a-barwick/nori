## Pending decisions for Austin

Mechanisms for all four are built configurable. No recommendation is adopted as a production default until Austin resolves it.

| ID | Question | Recommendation in r0 | Interim mechanism |
| --- | --- | --- | --- |
| D1 | Where connected-account credentials live | r0: deployment secret store for refresh tokens and app passwords with owner-scoped references in records. Backend recommends instead envelope-encrypted credential rows in the existing database with a KMS key in production, because refresh compare-and-swap, authorization epoch and disconnect must be atomic with the connection row and the secret store cannot add versions conditionally; integration notes the database option has fewer failure modes to prove. Both positions are open for Austin. | Credential store behind an interface with create, replace at expected version, read, delete and per-connection refresh locking. Local development uses an encrypted local file store so OAuth flows can be exercised. No production backend is written until D1 is resolved. |
| D2 | Standing authority for automations | A direct explicit request authorizes its actions without a second confirmation; an automation holds only what was shown at creation; expanded access returns to the user. | Creation materializes permission rules with explicit selectors and `max_operations`; occurrence tasks carry only that authority. `NORI_AUTOMATION_UNATTENDED=require_rule\|confirm_writes`, default `confirm_writes` until resolved, which turns unattended writes into interactions that expire at the execution window. Acceptance rows A25, A30 and A44 will say "interim D2" until then. Observed consequence: under the interim `NORI_USER_SENDS=ask`, a direct explicit request such as "create the event and invite the guest" still stops for approval before the send; that is the interim mechanism, not r0's recommendation, and it is exactly what D2 decides. |
| D3 | Missed automation runs | Catch up the latest read or summary run; deliver reminders only within their useful window; expire unattended writes outside their window; show missed work. | `missed_run` is required on every definition (`skip`, `latest`, `all`), so the API has no default; the creation screen shows the choice in plain words, preselected once Austin answers. Skipped and expired occurrences carry a reason. |
| D4 | What disconnect retains | Keep saved Library results and action history, stop future access, remove transient caches, offer separate deletion of imported content. | Disconnect always closes admission first; `purge_cache` and `delete_imported` flags default to false; saved items show `copied` provenance and the source connection's status. Backend, frontend and integration all support r0 here. |

## Design decisions recorded

| Decision | By | Content |
| --- | --- | --- |
| No web pass-through for the Nori MCP endpoint | frontend, agreed by backend and integration | `POST /mcp` is exposed from core's own ingress when hosted, with the client token as the only credential. The web origin sits behind the user's sign-in, and a route forwarding unauthenticated bearer requests would be a new public surface. A forward-only route through the web origin can be added if Austin wants it. Not a disagreement; recorded for Austin's awareness. |
| A10 hosted managed stdio MCP is blocked, not deferred | backend, agreed by coordinator | Hosted managed stdio needs declared-host egress enforcement in the guest sandbox; the sandbox currently enforces no network at all, and stdio servers run only on the local development stack. One egress-allowlist mechanism serving both A07 and A10 is the agreed design but needs an egress proxy inside the guest's network namespace plus install-review wiring, which is beyond this pass. Hooks with deadlines remain open on backend's list. |

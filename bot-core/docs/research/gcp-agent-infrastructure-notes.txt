I'd make the assistant's computer a per-user resource, not necessarily a per-conversation resource. That preserves tools, workspace files, and execution context across multiple conversations.

Why this category is exploding
Traditional cloud infrastructure assumed your unit of deployment was an application or service.

Agent infrastructure introduces a different unit: a computer belonging to a user, task, or agent.

That changes the infrastructure requirements considerably:

Provision isolated execution environments in seconds or less.

Maintain files, installed packages, and optionally running processes.

Suspend execution when waiting for an LLM response or human approval.

Restore state without paying for an always-running machine.

Snapshot and fork environments to explore multiple solutions.

Restrict network access, filesystem access and credential exposure.

AWS launched Lambda MicroVMs in June, Microsoft and Vercel have released managed alternatives, AWS upgraded AgentCore Runtime in September, and Google announced Agent Compute Engine in October. That's strong evidence that the major providers are investing in this compute model, although it doesn't establish broad adoption by itself.

1. Agent Substrate on GKE — how integrated is it?
It's more than an open-source framework someone happens to run on Kubernetes.

Google maintains a dedicated substrate-gke installer. It can provision a new GKE Standard cluster, configure the storage and networking dependencies, and deploy the Substrate control plane.

The installer provisions:

GKE cluster, node configuration, IAM and Workload Identity

Cloud Storage buckets for suspended agent snapshots

ActorTemplate and WorkerPool Kubernetes custom resources

Agent identity, mTLS certificates and networking components

PostgreSQL for actor and worker metadata

Monitoring dashboards and telemetry integration

Important distinction: This is an integrated installer, not a fully managed GKE add-on. You still own the installed Substrate controllers and their operational lifecycle. Cloud Hypervisor microVM execution also requires additional manual configuration; the default installation uses gVisor.

Self-Hosted Agent Substrate on Kubernetes
Architecture proposal | AWS EKS / GKE Standard / Kubernetes | October 24, 2026

Objective: Provide each user with a persistent, isolated Linux execution environment for an AI assistant, without dedicating an always-running VM to every user.

Status: Evaluation candidate. Agent Substrate is pre-1.0 and lacks broadly available production support. Do not adopt for customer production until release maturity, operational readiness, and security requirements are satisfied.

1. Infrastructure
Application layer: Next.js/mobile frontend, API service, authentication, agent orchestration, queues, task scheduler and tool gateway.

Agent Substrate: API server, actor registry, routing, controllers, warm worker pools, sandbox runtimes, RAM/filesystem checkpointing and restoration.

Supporting infrastructure:

Component	AWS	GCP
Kubernetes	EKS	GKE Standard
Worker compute	EC2 + Karpenter	Compute Engine + Autoscaler
Agent isolation	gVisor / Cloud Hypervisor	gVisor / Cloud Hypervisor
Snapshot storage	S3	Cloud Storage
Metadata / memory	RDS PostgreSQL	Cloud SQL PostgreSQL
Edge / networking	ALB/NLB, VPC	Cloud Load Balancing, VPC
Observability	CloudWatch / OpenTelemetry	Cloud Monitoring / OpenTelemetry
Execution lifecycle: User request → resolve actor → acquire warm worker → restore agent → execute → checkpoint RAM/filesystem → release worker. Conversations, scheduled jobs, durable documents and user identity remain external to the runtime.

2. Capabilities
Agent Substrate provides persistent actors, warm-worker multiplexing, isolated OCI execution, memory and filesystem snapshots, on-demand restoration, routing and runtime-level identity.

Custom agent harnesses can run Python, shell commands, browser automation, development tools and MCP integrations.

The application must still implement agent reasoning loops, memory retrieval, OAuth connectors, tool authorization, background scheduling, usage limits and billing.

3. Portability
The open-source core targets standard Kubernetes and supports both GCS and S3 snapshot backends. Google's integrated installer is GKE-specific.

On EKS or another Kubernetes distribution, the team owns installation, storage/IAM integration, node compatibility, networking policies, upgrades and validation.

Start with gVisor. Evaluate hardware microVMs separately because Cloud Hypervisor requires appropriate host virtualization support.

4. Pitfalls and limitations
Risk	Implication
Pre-1.0 maturity	Breaking API changes and operational instability possible
Security	Isolation is necessary but insufficient; validate egress enforcement, credentials and tenant boundaries
Hibernate/resume	Open network connections are not preserved; reconnect after restoration
Persistence	Large snapshots increase storage usage and wake latency
GPU	GPU passthrough and live CUDA checkpointing are unsupported
Operations	Team owns upgrades, observability, recovery, capacity and snapshot compatibility
Portability	Cloud-specific Kubernetes APIs, IAM, node capabilities and storage integration require validation
GKE's current documentation also identifies unsupported egress-policy and credential-injection capabilities despite related functionality appearing in the upstream project.

5. Estimated monthly cost
Example: 5,000 registered users, 250 peak concurrent agents, 0.25–0.5 vCPU and 0.5–1 GiB RAM per active agent.

Cost component	Monthly estimate
EKS worker nodes (6–12 m7i.4xlarge)	$3,533–$7,066
Kubernetes management	~$73
S3 snapshots (5–10 TiB)	~$118–$236
PostgreSQL, networking, disks, telemetry	$400–$2,000+
Total infrastructure	~$4,000–$10,000+
Illustrative AWS on-demand pricing, excluding model inference, external services, browser bandwidth, discounts and labor. Actual sizing requires workload benchmarks. GCP will have different worker-node prices.

6. Adoption criteria
Before production, validate tenant isolation, credential boundaries, checkpoint/recovery correctness, p95/p99 resume time, cross-node restoration, operational upgrades, snapshot cost, scaling and availability.

Recommendation: Retain Agent Substrate as a future execution-layer option. Prototype on disposable infrastructure if useful, but require a supported production release and proven security controls before customer deployment.

References: Upstream project · GKE limitations · EKS pricing · GKE pricing

The important architectural point is that Agent Substrate replaces execution infrastructure, not the assistant application. Its multiplexing model is what makes thousands of persistent assistants economically plausible, but it also introduces a new scheduling, storage and recovery system that your team must operate.

The cost estimates use current EKS and EC2 pricing. The portability and maturity qualifications come from the upstream repository and Google's deployment documentation.
